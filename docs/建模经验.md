## 1. 屏幕映射与长度换算（最常用，先背这个）

```
世界 (x, y)  →  屏幕 ( (y−x)·128 , (x+y)·64 )        // tilePx = 256（4x 档）
1 格 = 16 世界单位 = 13.9 m
```

**这个映射是各向异性的** —— 同一个世界长度，方向不同，屏幕长度不同：

| 方向 | 屏幕位移 | 屏幕长度 |
|---|---|---:|
| 沿世界 `x` | `(−128, +64)` | 143.1 px |
| 沿世界 `y` | `(+128, +64)` | 143.1 px |
| 沿对角 `(1,1)/√2` | `(0, +90.5)` | **90.5 px** |
| 沿对角 `(1,−1)/√2` | `(−181, 0)` | **181.0 px** |

**做轨道时真正要用的量是「横断面」的换算法**（= 垂直于钢轨方向的 1 格世界长度是几 px）：

| 朝向 | 横断面在屏幕上的方向 | 1 格 | 系数 |
|---|---|---:|---:|
| `TRACK_X` / `TRACK_Y`（整格对角） | `(∓1, 2)/√5` | **114.5 px** | `256/√5` |
| `TRACK_UPPER` / `TRACK_LOWER`（屏幕上水平带） | 竖直 `(0,1)` | **90.5 px** | `128/√2` |
| `TRACK_LEFT` / `TRACK_RIGHT`（屏幕上竖直带） | 水平 `(1,0)` | **181.0 px** | `256/√2` |

> ⚠ **同一个 `.model`，4 个朝向的观感厚度差近 2 倍。** 实测 `probe_half_upper`：
> `v0/v2`（UPPER/LOWER）内容 **166 × 21**，`v1/v3`（LEFT/RIGHT）**40 × 84** ——
> 道床带一个 21 px 厚、一个 40 px 厚。
>
> **这不是模型的毛病，是投影的固有性质。** 屏幕映射的矩阵
> `M = [[−128, 128], [64, 64]]`，`MᵀM` 的特征值是 `8192` 与 `32768`
> ⇒ 奇异值 **σ_min = 90.5、σ_max = 181.0，比值恰好 2.0**。
> 也就是说：**同一段世界长度，沿 NE–SW 方向投影出来是沿 NW–SE 方向的 2 倍长。**
> 这个 2 倍来自 OpenTTD 的 2:1 压扁，**任何** OpenTTD 素材（含参照包、xUSSR）都一样。
>
> **对建模的实际影响**：调尺寸时**不能只用一个 px/格 的系数** —— 必须按当前朝向
> 取 §1 表里对应的那个（114.5 / 90.5 / 181.0），否则会把"朝向差异"误判成
> "我们的轨道比参照宽/窄"。**本轮就在这里量错过一次。**

**怎么量**：别看 bbox 猜。在轨道正中间取 `|u| ≤ 8 px` 的窄窗，把 alpha 像素投影到
`(u=沿轨, v=垂直)` 两个轴上，量 `v` 的跨度 —— 那才是横断面厚度。

## 2. 比例：横断面才是"像不像"的关键

真实单线有砟轨道的横断面（1 格 = 13.9 m）：

| 部件 | 实物 | 世界格 |
|---|---:|---:|
| 轨枕长 | 2.50 m | 0.180 |
| 轨距（轴线间距） | 1.435 m | 0.1032 |
| 轨头宽 | ~0.11 m | 0.008 |
| 道床顶宽 | 3.4–3.8 m | 0.25–0.27 |
| 钢轨高 | ~0.18 m | 0.013 |

**判断"像不像"的唯一可靠指标是「枕木长 / 道床宽」这个比值**，不是任何绝对像素数：

| | 道床 | 枕木 | 枕木/道床 |
|---|---:|---:|---:|
| 我方直线轨 `probe_track_x` | 51 px | 23 px | **45%** |
| 我方半格轨 收窄前 | 21 px | 16 px | **78%** ← 枕木撑满道床，看着"胖" |
| 我方半格轨 收窄后（×1/√2） | 21 px | 13 px | **62%** |
| 参照包 半格 | 32 px | — | — |

> **踩过的坑（2026-09，两轮）**：用户说"斜向的显得宽"，我连着两次只收**道床**，
> 结果枕木相对道床反而更满，观感更糟。用户点破："你只是收了道床，没有缩放枕木和铁轨。"
>
> **教训**：横断面有**三个独立的旋钮** —— 道床宽、枕木长、轨距。用户说"宽"时
> 必须问清是哪一层，或者直接量这个比值给他看，**不要猜着拧道床**。

轨距这一项有额外约束：车辆精灵是别的 GRF 画的，轮距按标准轨距 1.435 m。
但在 OpenTTD 里斜向本来就带缩放（见 §6），所以**以"图像看上去一致"为准**是合理的，
人工裁定过一次：半格轨横断面整体乘 `1/√2`。

## 3. 高度：贴地，不抬高

```
钢轨顶   z = 0.0230 格 ≈ 3.6 px @4x
钢轨底   z = 0.0100
轨枕顶   z = 0.0100                    ← 钢轨坐在枕木顶上，这个值一动钢轨就得跟着动
轨枕底   z = 0.0000
道床     z = 0.0005 ~ 0.006（贴地饰面，靠倾斜小面做出起伏）
```

> **2026-09 人工裁定：枕木不是"做薄"，而是「连带钢轨整体下移」。**
> 钢轨 + 枕木当作**一个刚体**往下挪 `0.0040`（枕木底 0.0040 → 0.0000，正好落到地面）：
>
> | 部件 | 下移前 | 下移后 |
> |---|---|---|
> | 枕木 | 0.0040 → 0.0140 | **0.0000 → 0.0100**（厚度 0.0100 不变） |
> | 钢轨 X 组 | 0.0140 → 0.0270 | **0.0100 → 0.0230**（高 0.0130 不变） |
> | 钢轨 Y 组（交叉） | 0.0150 → 0.0280 | **0.0110 → 0.0240**（叉口保持 +0.0005 定序差） |
>
> ⚠ **下移量的上限就是 `0.0040`** —— 枕木底再往下就穿到地面以下了。
> 想再低只有两条路：改"做薄"（把底抬上去），或者压低钢轨本身的高度。

- **绝不抬高地基**：瓦片内抬高的几何在跨瓦片绘制时会被邻格精灵遮挡 ⇒ 图形错位。
- OpenTTD 的竖轴是压缩的（`TILE_SIZE=16` / `TILE_HEIGHT=8`），同一个 z，flatiso 画出来
  是它的 **2.45 倍**。所以高度一律做小。
- 想要"不规则表面"，**不加高度**，改用**贴地的小多边形**当碎石散粒（抬 `0.002` 防 z-fighting），
  靠材质冷暖差 + `grain` 出颗粒感。
- ⚠ **有高度就难对齐**：钢轨/枕木是精灵里唯一必须首尾严格对上的细线，任何 1px 的
  放置差都会在瓦片边界变成一个看得见的台阶；道砟是宽而低对比的面，同样的 1px 看不出来。
  所以"轨道显得高"本身不是问题，**"有必须对齐的细线"才是**。

## 4. 道砟的几何形状

- 道床是**沿钢轨方向的板带**（`TRACK_X` ⇒ `y ∈ [0.32, 0.68]`；半格 ⇒ `x+y ∈ [0.35, 0.65]`）。
  **不是**瓦片角上的三角形 —— 早期做半格轨时按角三角形做，出来是顶"尖帽子"，全错。
- 边缘做**微微折线**：外围两行逐列扰动 ±0.008~0.012 格，比直线看着自然。
- 坡脚散粒用小而暗的 prism（0.014 见方、高 0.005），只用 `gravel` / `stone_dark`。

### 4.5 引擎怎么取图：交叉与道岔**不一样**（核自源码）

`rail_cmd.cpp:3784-3816`：

```cpp
case TRACK_BIT_CROSS: DrawGroundSprite(ground + RTO_CROSSING_XY, ...); break;  // 交叉：**只画 underlay**
default:  // 道岔
    DrawGroundSprite(ground + RTO_JUNCTION_SW/NE/SE/NW/NSEW, ...);   // **只画道砧**
    if (track & TRACK_BIT_X)     DrawGroundSprite(overlay + RTO_X, ...);
    if (track & TRACK_BIT_UPPER) DrawGroundSprite(overlay + RTO_N, ...);
    ...
```

| 槽位 | underlay 里要放什么 | 钢轨谁画 |
|---|---|---|
| `RTO_CROSSING_XY` | **道砧 + 两组钢轨（烘进去）** | 没有 overlay ⇒ 必须烘 |
| `RTO_JUNCTION_*` | **只有道砧** | 引擎逐段叠 `overlay` 的 X/Y/N/S/E/W |

→ **道岔模型里绝不能烘钢轨**，否则与 overlay 双画。`rail.h:84-89` 的注释也写着：
`RTO_CROSSING_XY ///< Crossing of X and Y rail, **with ballast**` 而 `RTO_JUNCTION_SW ///< **Ballast** for junction`。

### 4.6 道岔的三个形状其实是同一个模型的四个旋转

对着 `rail_cmd.cpp` 的判据 + `TRACK_BIT_3WAY_*` 反推，每个槽位对应的瓦片轨位组合：

| 槽位 | 轨位组合 |
|---|---|
| `JUNCTION_SW` | `Y · LOWER · LEFT` |
| `JUNCTION_NE` | `Y · UPPER · RIGHT` |
| `JUNCTION_SE` | `X · LOWER · RIGHT` |
| `JUNCTION_NW` | `X · UPPER · LEFT` |
| `JUNCTION_NSEW` | 上面四种「箭头」组合 + 全 6 位 |

用四重旋转 `R`（`X→Y, UPPER→RIGHT→LOWER→LEFT`）代入（`R: (u=x+y, v=y−x) → (1+v, 1−u)`）：

```
R³(SW={Y,LOWER,LEFT}) = {X,RIGHT,LOWER} = SE      R²(SW) = {Y,UPPER,RIGHT} = NE
R¹(SW) = {X,LEFT,UPPER}  = NW
```

⇒ **4 个三向道岔 = 同一个模型的 4 个朝向**（不是 4 个独立形状）。
取图顺序：`SW←v0, SE←v1, NE←v2, NW←v3`。

### 4.7 道砧形状 = 各轨位板带的并集（人工裁定）

道岔道砧 = 该瓦片各轨位对应板带的并集（X/Y 用直线带，半格用半格带）。
实现：**32×32 网格 + 「格心是否落在并集内」判据** ⇒ 每格只出一面，
天然没有重叠面 / z-fighting（就是「叠加多个方向模型后去掉看不见的面」）。
一个生成器参数化了板带集合，交叉/三向/四向三个模型全出。

### 4.8 每方向偏移：单朝向可以手调，**多朝向共用的必须烘进几何**

实机手调发现：**不同方向需要的偏移不一样**（相对按 `centerAnchor` 算出的 `-131,-19`，单位 4x 像素）：

| 方向 | 用途 | 需要的屏幕偏移 |
|---|---|---:|
| `TRACK_X` | 整格对角（沿世界 x） | **+4, −1** |
| `TRACK_Y` | 整格对角（沿世界 y） | **−4, +2** |
| `TRACK_UPPER` | 屏幕上水平带（上） | +3, −2 |
| `TRACK_LOWER` | 屏幕上水平带（下） | +2, −2 |
| `TRACK_LEFT` / `TRACK_RIGHT` | 屏幕上竖直带 | 0, 0 |

- **单朝向精灵**（如 `probe_track_x_v0` 只管 `RTO_X`）⇒ 直接在 `templates.pnml` 那一行改 `xrel/yrel`，标 `【手调】`。
- **多朝向共用的精灵**（`G1_crossing` 一张图里同时有 X 和 Y 两套轨道；道岔同理）
  ⇒ 一张精灵只能有一个 `xrel/yrel`，**两个方向的偏移无法分别用模板修正**
  ⇒ 必须**烘进模型坐标**。

**工具**：`tools/gen-g1-switches.mjs` 顶部的 `DIR_DELTA` 表（唯一口径），改完跑 `make switches`。

换算：屏幕 `(dx,dy)` ↔ 世界 `(wx,wy)`：`dx=(wy−wx)·128`、`dy=(wx+wy)·64`
⇒ `wx=(dy/64−dx/128)/2`、`wy=(dy/64+dx/128)/2`。工具里有**反算自检**。
例：`(+2,−3)` px ⇒ 世界 `(−0.03125, −0.01563)`。

> ⚠ 挪位后几何必然探出瓦片 ⇒ 生成时会**剪裁到 `[0,1]`**（flatiso 铁律）。
> 剪掉的缺口在实机里由**邻格精灵的溢出**盖住（OpenTTD 轨道精灵本来就互相重叠，
> 263px 的格位才装得下 256px 的瓦片）。不剪的话 flatiso 会报 `超出占地`。

### 4.9 补空白：挪之后必须把留下的空白填上（人工裁定）

整体挪位后，几何在一端探出瓦片、另一端留下空白。**绝不能直接剪掉就完事**（那就是“缺一块”）。

| 部件 | 怎么补 |
|---|---|
| 钢轨 / 道砧（连续） | 预位移范围回扩同样的量 ⇒ 位移完正好还铺满 `[0,1]`。侧面效果是纵向那截被抵消 |
| 柕木（周期性） | 位置 = `0.012 + k·间距 + 纵向位移`，只保留落在 `[0.012,0.988]` 的 ⇒ **相位跟着位移走**，末端不够就多铺一根 |

实现在 `tools/gen-g1-switches.mjs` 的 `alongRange()` / `sleeperBoxes()`，
并有 `clipBox()` 计数器：**正常情况下应该是 0 处被剪**。

调试开关（出对照图用，别拿它生成正式模型）：
```
G1_SWITCHES_ZERO=1    node tools/gen-g1-switches.mjs   # 零偏移（= 改动前）
G1_SWITCHES_NOFILL=1  node tools/gen-g1-switches.mjs   # 只挪不补（会留空白）
```

> ⚠ **一个容易误会的几何事实**：屏幕位移 `(dx,dy)` 振开看是“横着挪多少”，实际上分解到**轨道自己的轴**上才是真正生效的部分。
> 例：`X = (+5,−2)` ⇒ **纵向 5.03 px + 横向 0.56 px**。
> 而柕木间距投影到屏幕是 5.82 px ⇒ 纵向那 5 px ≈ **0.86 个间距**，
> 看上去几乎一样。所以“改了但看不出”不一定是没改，而是这个偏移本就大部分沿轨。
> 工具会把每个方向的 纵向/横向 分量打印出来。

> ⚠ 这几个数还在收敛中：`probe_track_x#1` 目前是 `(+1,−1)` 而 `#3` 是 `(0,0)`，
> 两者都是 `TRACK_Y`，但 `#1` 引擎不用（`RTO_Y` 取 v3）。**收敛后只改那张表重跑。**

### 4.10 坡道：抬升量、基准朝向、以及**取图顺序不是顺序贴**

**抬升量**（实测参照包，不是推的）：
`test-pre_01` 内容高 129 px（平轨），`test-pre_up` 161 px ⇒ 一格坡抬 **32 px @4x**。
换算成 flatiso 的 z：`32 / 156.7673 = **0.2041 格**`。
反查一致：OpenTTD 坡抬 8/16 = 0.5，而 flatiso 竖轴是它的 2.4495 倍 ⇒ `0.5/2.4495 = 0.2041` ✓

**基准朝向**：`SLOPE_NE` = N 角与 E 角同时抬起。由角映射 N=(0,0)、E=(0,1)
⇒ 抬的就是 **x=0 那条边**。它的轨道是 `TRACK_X`（沿 x），正好垂直于抬边 ⇒ 顺坡走 ✓
于是基准模型写成 `z(x) = 0.2041·(1−x)`。

**取图顺序（坑）**：flatiso 的"朝向"是**绕占地中心旋转模型**
（`flatiso/core/raster.mjs:19-42`），90° 那一步是 `(x,y) → (1−y, x)`。
⇒ `view k` 把 view0 里位于角 C 的特征搬到 `R^(−k)(C)`，`R` 就是引擎的四重旋转（北→东→南→西）。
view0 抬的是 N–E 边，于是：

| view | 抬起的边 | ≈屏幕 | 对应槽位 |
|---|---|---|---|
| v0 | x=0（N–E） | 右上 | `RTO_SLOPE_NE` |
| v1 | y=0（N–W） | 左上 | `RTO_SLOPE_NW` |
| v2 | x=1（S–W） | 左下 | `RTO_SLOPE_SW` |
| v3 | y=1（S–E） | 右下 | `RTO_SLOPE_SE` |

而**引擎的槽位顺序是 `NE / SE / SW / NW`**（`rail.h:80-83`）
⇒ 喂图是 `v0, v3, v2, v1`，**槽 7 要 v3、槽 8 要 v2**，不是顺序贴。

> **怎么自查**：别靠眼睛看"哪头高"。屏幕 y = `64(x+y) − 156.7673·z`，
> z 高和"靠后"**都会让像素往上跑**，两者会互相抵消，肉眼看反。
> 直接把四个 view 的**最高像素坐标**算出来对：以瓦片原点为基准，
> 预测 `v0=(41,−11.6)  v1=(−41,−11.6)  v2=(41,20)  v3=(−41,20)`，
> 实渲量到 `(40,−13) (−43,−11) (38,20) (−37,20)` ✓（量法见 `out/slope-dir.mjs`）

## 5. 材质与颗粒

- **`GRAIN_SCALE` 是"世界单位下的格子尺寸"**，不是强度。1 个输出 px ≈ 0.0070 世界单位
  ⇒ 想要 ~1.4 px 的颗粒，取值 **0.010**。早期填 0.7 得到 100 px 的大色块。
- `GRAIN_AMOUNT` 是**材质自身幅度的倍数**（`gravel` 幅度 0.060）。
- 平面着色（flat shading）**没有贴图** ⇒ 想加细节只能加面。所以"加面数"之前先分清
  要加的是哪一层的面，否则只是白烧面数。
- 轨枕分段用**几乎同色**的 `wood_dark`(122,85,48) / `wood_seam`(133,95,49)；
  用 `wood`(169,121,63) 会把接缝衬得像断成三截。
- 钢轨：顶面 `metal`、侧面 `rust`（黄锈）。

## 7. 工作法（可复用）

### 7.1 「生成器写在 `out/`，`.model` 只放字面量」

flatiso 的铁律是**模型是手写字面量，不是生成器**。但手算 84 个 quad 的坐标不现实。

**做法**：临时 Node 脚本（写在 `out/`，gitignore 的）算出所有坐标，**一次性打印成
完整的 `.model` 文本**写入 `models/`。结果是：

- `models/*.model` 里**只有字面量** ✓ 铁律满足
- 坐标由程序算，不会手抄错 ✓
- 参数（带宽、枕木长、轨距、分段数）留在脚本里，**改一个数就能整版重算** ✓
  —— 本轮"道床 0.48 → 0.34 → 0.30"和"横断面 ×1/√2"全靠这个迭代得动

### 7.2 三个诊断图

| 图 | 命令 | 看什么 |
|---|---|---|
| `out/calibrate/anchors.png` | `make diag` | 洋红十字=瓦片菱形、绿十字=瓦片中心压在每个 模型×朝向 上 ⇒ **摆没摆对** |
| `out/calibrate/compare.png` / `compare_zoom_*.png` | `make diag` | 参照包 / xUSSR×4 / 我方 / 叠加，同一锚点 ⇒ **像不像**（量宽窄必须用 zoom 版） |
| `out/calibrate/index.png` | `make sprites` | **偏移索引图**：每个 模型×朝向 一格，全画在同一瓦片锚点上。格内：洋红菱形=瓦片轮廓、**黄十字 + 每 8px 刻度 = 瓦片原点**、蓝格=每 16px（64px 标数）、左上角青点数=朝向号+1；格下三行直写着 `模型#朝向` / `xrel,yrel` 与 **templates.pnml 行号** / `rect`，手调过的行标 `*TUNED*` ⇒ **查名字 + 直接调偏移** |

三个都在 `out/`，**`make clean` 会删掉**，用时重建。
索引图默认 2 倍，改 ±1~2 px 时用 `node tools/sprites.mjs --sheet --zoom 3` 更清楚。
图里的字是 `tools/font5x7.mjs` 里手搓的 5×7 点阵字体（只有大写 + 数字 + 少量符号），
所以标注一律大写、不含中文。

### 7.3 摆放与对账

- 摆放事实在**手写**的 `src/rails/templates.pnml`（人工裁定 O2，无生成器）。
- 手调某一行 ⇒ 在行尾注释写 **`【手调】`**，`make check` 就不再把那行当漂移报。

#### ★★ 新规矩（人工裁定 2026-09）：`templates.pnml` 完全归人管，脚本一律不准写它

| # | 规矩 |
|---|---|
| 1 | **任何脚本/工具都不准写 `templates.pnml`**（`tools/*.mjs` 只读它） |
| 2 | **唯一允许改它的情形**：**新增精灵类型**（新增 `.model`）—— 图集重排，`rect` 必须同步 |
| 3 | 其余一切改动（几何、偏移、高度、材质…）**只改模型**，不许动模板 |

**为什么这条规矩成立**：flatiso 的图集**只在「模型数量/顺序」变化时重排**。
只改模型几何 —— **哪怕大幅改高度** —— `rect` 一个都不会变。已实测两次：

- `9901c13` 道床基准 z 0.0020→0.0005（5 个模型整体降高度）⇒ `rect` 全不变
- 本次把**所有枕木 z 0.0040→0.0100**（厚度减 60%）⇒ `rect` 全不变

**偏移写在哪，按「一张模板管几个方向」分**：

| 精灵 | 一张模板管几个方向 | 偏移写在 |
|---|---|---|
| `probe_track_x` / `probe_half_upper` / `G1_rail_straight` / `G1_rail_halftrack` | **1 个** | `templates.pnml`（Sprite Aligner 手调，那是人的活） |
| `G1_crossing` / `G1_junction3` / `G1_junction4` | **多个** | **模型几何**（`tools/gen-g1-switches.mjs` 的 `DIR_DELTA`），模板**留基准 `-131,-19`** |

> ⚠ 两边都写 = 双重应用 ⇒ 表现是"**每修正一次就多偏一份**"（踩过，见 `9747e19`）。
> ⚠ 只改多方向精灵、不同步单方向精灵 ⇒ 表现是"**接缝处道床有缝、钢轨连着**"。
>   但**同步也必须在模型侧做**（改 `DIR_DELTA`），不准去改模板。

### 7.4 工具链的硬约束

| 约束 | 说明 |
|---|---|
| `nmlc` 不自带预处理器 | `#include` / `#define` 必须先过 `gcc -E -x c -I.` |
| `quad` 要 **12 个空格分隔的数** | `poly` / `prism` 收的是 `x,y` 点对，别搞混 |
| `poly` **不支持 `\` 续行** | 必须写成一整行 |
| `models/` 必须**平铺** | `listModelFiles()` 不递归；几何组用文件名前缀（`G1_*`） |
| 改 railtype 后**必须** `make check` | railtype 错了编译零报错，游戏里表现为"车库里一辆车都没有" |

### 7.5 判编码：以字节为准，别信终端

`Get-Content` 在 PowerShell 5.1 下按 **ANSI 码页**读 UTF-8 文件，**必然**把中文显示成
乱码（`鈥斺€?`）。本轮据此误判过一次"文件坏了"，其实文件完好。
**一律用 `node -e` 或 `make check` 复核**，`make check` 有编码自检。

## 8. 一次建模的标准流程（照抄）

1. **过 D11 确认门** —— 该组的道床/轨枕/钢轨/隧道口 + C8 四项，人工确认后才动手。
2. 在 `out/` 写一次性生成脚本，参数化（带宽/枕木/轨距/分段）。
3. 生成 `models/G?_xxx.model` → `make sprite` 渲染。
4. `make diag` 看 `anchors.png` 摆位 → 看 `compare_zoom_*.png` 比比例。
5. 比例不对 ⇒ **回 §2 分清是哪个旋钮**，改脚本参数重算，别手改坐标。
6. `make sprites` 核对锚点（模型尺寸一变，锚点就会动），必要时更新 `templates.pnml`。
7. `make` + `make check` 全绿。
8. **实机看** —— 最终判据在游戏里，不在数字上。
