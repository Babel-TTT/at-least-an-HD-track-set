## 1. 屏幕映射与长度换算（最常用，先背这个）

```
世界 (x, y)  →  屏幕 ( (y−x)·128 , (x+y)·64 )        // tilePx = 256（4x 档）
1 格 = 16 世界单位 = 13.9 m
```

**这个映射是各向异性的** —— 同一个世界长度，方向不同，屏幕长度不同：

| 方向 | 屏幕位移 | 屏幕长度 |
|---|---|---:|
| 沿世界 `x` | `(−128, +64)` | 143.1 px |
| 沿世界 `y` | `(+128, +64)` | 143.1 px |
| 沿对角 `(1,1)/√2` | `(0, +90.5)` | **90.5 px** |
| 沿对角 `(1,−1)/√2` | `(−181, 0)` | **181.0 px** |

**做轨道时真正要用的量是「横断面」的换算法**（= 垂直于钢轨方向的 1 格世界长度是几 px）：

| 朝向 | 横断面在屏幕上的方向 | 1 格 | 系数 |
|---|---|---:|---:|
| `TRACK_X` / `TRACK_Y`（整格对角） | `(∓1, 2)/√5` | **114.5 px** | `256/√5` |
| `TRACK_UPPER` / `TRACK_LOWER`（屏幕上水平带） | 竖直 `(0,1)` | **90.5 px** | `128/√2` |
| `TRACK_LEFT` / `TRACK_RIGHT`（屏幕上竖直带） | 水平 `(1,0)` | **181.0 px** | `256/√2` |

> ⚠ **同一个 `.model`，4 个朝向的观感厚度差近 2 倍。** 实测 `probe_half_upper`：
> `v0/v2`（UPPER/LOWER）内容 **166 × 21**，`v1/v3`（LEFT/RIGHT）**40 × 84** ——
> 道床带一个 21 px 厚、一个 40 px 厚。
>
> **这不是模型的毛病，是投影的固有性质。** 屏幕映射的矩阵
> `M = [[−128, 128], [64, 64]]`，`MᵀM` 的特征值是 `8192` 与 `32768`
> ⇒ 奇异值 **σ_min = 90.5、σ_max = 181.0，比值恰好 2.0**。
> 也就是说：**同一段世界长度，沿 NE–SW 方向投影出来是沿 NW–SE 方向的 2 倍长。**
> 这个 2 倍来自 OpenTTD 的 2:1 压扁，**任何** OpenTTD 素材（含参照包、xUSSR）都一样。
>
> **对建模的实际影响**：调尺寸时**不能只用一个 px/格 的系数** —— 必须按当前朝向
> 取 §1 表里对应的那个（114.5 / 90.5 / 181.0），否则会把"朝向差异"误判成
> "我们的轨道比参照宽/窄"。**本轮就在这里量错过一次。**

**怎么量**：别看 bbox 猜。在轨道正中间取 `|u| ≤ 8 px` 的窄窗，把 alpha 像素投影到
`(u=沿轨, v=垂直)` 两个轴上，量 `v` 的跨度 —— 那才是横断面厚度。

## 2. 比例：横断面才是"像不像"的关键

真实单线有砟轨道的横断面（1 格 = 13.9 m）：

| 部件 | 实物 | 世界格 |
|---|---:|---:|
| 轨枕长 | 2.50 m | 0.180 |
| 轨距（轴线间距） | 1.435 m | 0.1032 |
| 轨头宽 | ~0.11 m | 0.008 |
| 道床顶宽 | 3.4–3.8 m | 0.25–0.27 |
| 钢轨高 | ~0.18 m | 0.013 |

**判断"像不像"的唯一可靠指标是「枕木长 / 道床宽」这个比值**，不是任何绝对像素数：

| | 道床 | 枕木 | 枕木/道床 |
|---|---:|---:|---:|
| 我方直线轨 `probe_track_x` | 51 px | 23 px | **45%** |
| 我方半格轨 收窄前 | 21 px | 16 px | **78%** ← 枕木撑满道床，看着"胖" |
| 我方半格轨 收窄后（×1/√2） | 21 px | 13 px | **62%** |
| 参照包 半格 | 32 px | — | — |

> **踩过的坑（2026-09，两轮）**：用户说"斜向的显得宽"，我连着两次只收**道床**，
> 结果枕木相对道床反而更满，观感更糟。用户点破："你只是收了道床，没有缩放枕木和铁轨。"
>
> **教训**：横断面有**三个独立的旋钮** —— 道床宽、枕木长、轨距。用户说"宽"时
> 必须问清是哪一层，或者直接量这个比值给他看，**不要猜着拧道床**。

轨距这一项有额外约束：车辆精灵是别的 GRF 画的，轮距按标准轨距 1.435 m。
但在 OpenTTD 里斜向本来就带缩放（见 §6），所以**以"图像看上去一致"为准**是合理的，
人工裁定过一次：半格轨横断面整体乘 `1/√2`。

## 3. 高度：贴地，不抬高

```
钢轨顶   z = 0.0230 格 ≈ 3.6 px @4x
钢轨底   z = 0.0100
轨枕顶   z = 0.0100                    ← 钢轨坐在枕木顶上，这个值一动钢轨就得跟着动
轨枕底   z = 0.0000
道床     z = 0.0005 ~ 0.006（贴地饰面，靠倾斜小面做出起伏）
```

> **2026-09 人工裁定：枕木不是"做薄"，而是「连带钢轨整体下移」。**
> 钢轨 + 枕木当作**一个刚体**往下挪 `0.0040`（枕木底 0.0040 → 0.0000，正好落到地面）：
>
> | 部件 | 下移前 | 下移后 |
> |---|---|---|
> | 枕木 | 0.0040 → 0.0140 | **0.0000 → 0.0100**（厚度 0.0100 不变） |
> | 钢轨 X 组 | 0.0140 → 0.0270 | **0.0100 → 0.0230**（高 0.0130 不变） |
> | 钢轨 Y 组（交叉） | 0.0150 → 0.0280 | **0.0110 → 0.0240**（叉口保持 +0.0005 定序差） |
>
> ⚠ **下移量的上限就是 `0.0040`** —— 枕木底再往下就穿到地面以下了。
> 想再低只有两条路：改"做薄"（把底抬上去），或者压低钢轨本身的高度。

- **绝不抬高地基**：瓦片内抬高的几何在跨瓦片绘制时会被邻格精灵遮挡 ⇒ 图形错位。
- OpenTTD 的竖轴是压缩的（`TILE_SIZE=16` / `TILE_HEIGHT=8`），同一个 z，flatiso 画出来
  是它的 **2.45 倍**。所以高度一律做小。
- 想要"不规则表面"，**不加高度**，改用**贴地的小多边形**当碎石散粒（抬 `0.002` 防 z-fighting），
  靠材质冷暖差 + `grain` 出颗粒感。
- ⚠ **有高度就难对齐**：钢轨/枕木是精灵里唯一必须首尾严格对上的细线，任何 1px 的
  放置差都会在瓦片边界变成一个看得见的台阶；道砟是宽而低对比的面，同样的 1px 看不出来。
  所以"轨道显得高"本身不是问题，**"有必须对齐的细线"才是**。

## 4. 道砟的几何形状

- 道床是**沿钢轨方向的板带**（`TRACK_X` ⇒ `y ∈ [0.32, 0.68]`；半格 ⇒ `x+y ∈ [0.35, 0.65]`）。
  **不是**瓦片角上的三角形 —— 早期做半格轨时按角三角形做，出来是顶"尖帽子"，全错。
- 边缘做**微微折线**：外围两行逐列扰动 ±0.008~0.012 格，比直线看着自然。
- 坡脚散粒用小而暗的 prism（0.014 见方、高 0.005），只用 `gravel` / `stone_dark`。

### 4.5 引擎怎么取图：交叉与道岔**不一样**（核自源码）

`rail_cmd.cpp:3784-3816`：

```cpp
case TRACK_BIT_CROSS: DrawGroundSprite(ground + RTO_CROSSING_XY, ...); break;  // 交叉：**只画 underlay**
default:  // 道岔
    DrawGroundSprite(ground + RTO_JUNCTION_SW/NE/SE/NW/NSEW, ...);   // **只画道砧**
    if (track & TRACK_BIT_X)     DrawGroundSprite(overlay + RTO_X, ...);
    if (track & TRACK_BIT_UPPER) DrawGroundSprite(overlay + RTO_N, ...);
    ...
```

| 槽位 | underlay 里要放什么 | 钢轨谁画 |
|---|---|---|
| `RTO_CROSSING_XY` | **道砧 + 两组钢轨（烘进去）** | 没有 overlay ⇒ 必须烘 |
| `RTO_JUNCTION_*` | **只有道砧** | 引擎逐段叠 `overlay` 的 X/Y/N/S/E/W |

→ **道岔模型里绝不能烘钢轨**，否则与 overlay 双画。`rail.h:84-89` 的注释也写着：
`RTO_CROSSING_XY ///< Crossing of X and Y rail, **with ballast**` 而 `RTO_JUNCTION_SW ///< **Ballast** for junction`。

### 4.6 道岔的三个形状其实是同一个模型的四个旋转

对着 `rail_cmd.cpp` 的判据 + `TRACK_BIT_3WAY_*` 反推，每个槽位对应的瓦片轨位组合：

| 槽位 | 轨位组合 |
|---|---|
| `JUNCTION_SW` | `Y · LOWER · LEFT` |
| `JUNCTION_NE` | `Y · UPPER · RIGHT` |
| `JUNCTION_SE` | `X · LOWER · RIGHT` |
| `JUNCTION_NW` | `X · UPPER · LEFT` |
| `JUNCTION_NSEW` | 上面四种「箭头」组合 + 全 6 位 |

用四重旋转 `R`（`X→Y, UPPER→RIGHT→LOWER→LEFT`）代入（`R: (u=x+y, v=y−x) → (1+v, 1−u)`）：

```
R³(SW={Y,LOWER,LEFT}) = {X,RIGHT,LOWER} = SE      R²(SW) = {Y,UPPER,RIGHT} = NE
R¹(SW) = {X,LEFT,UPPER}  = NW
```

⇒ **4 个三向道岔 = 同一个模型的 4 个朝向**（不是 4 个独立形状）。
取图顺序：`SW←v0, SE←v1, NE←v2, NW←v3`。

### 4.7 道砧形状 = 各轨位板带的并集（人工裁定）

道岔道砧 = 该瓦片各轨位对应板带的并集（X/Y 用直线带，半格用半格带）。
实现：**32×32 网格 + 「格心是否落在并集内」判据** ⇒ 每格只出一面，
天然没有重叠面 / z-fighting（就是「叠加多个方向模型后去掉看不见的面」）。
一个生成器参数化了板带集合，交叉/三向/四向三个模型全出。

### 4.8 每方向偏移：单朝向可以手调，**多朝向共用的必须烘进几何**

实机手调发现：**不同方向需要的偏移不一样**（相对按 `centerAnchor` 算出的 `-131,-19`，单位 4x 像素）：

| 方向 | 用途 | 需要的屏幕偏移 |
|---|---|---:|
| `TRACK_X` | 整格对角（沿世界 x） | **+4, −1** |
| `TRACK_Y` | 整格对角（沿世界 y） | **−4, +2** |
| `TRACK_UPPER` | 屏幕上水平带（上） | +3, −2 |
| `TRACK_LOWER` | 屏幕上水平带（下） | +2, −2 |
| `TRACK_LEFT` / `TRACK_RIGHT` | 屏幕上竖直带 | 0, 0 |

- **单朝向精灵**（如 `probe_track_x_v0` 只管 `RTO_X`）⇒ 直接在 `templates.pnml` 那一行改 `xrel/yrel`，标 `【手调】`。
- **多朝向共用的精灵**（`G1_crossing` 一张图里同时有 X 和 Y 两套轨道；道岔同理）
  ⇒ 一张精灵只能有一个 `xrel/yrel`，**两个方向的偏移无法分别用模板修正**
  ⇒ 必须**烘进模型坐标**。

**工具**：`tools/gen-g1-switches.mjs` 顶部的 `DIR_DELTA` 表（唯一口径），改完跑 `make switches`。

换算：屏幕 `(dx,dy)` ↔ 世界 `(wx,wy)`：`dx=(wy−wx)·128`、`dy=(wx+wy)·64`
⇒ `wx=(dy/64−dx/128)/2`、`wy=(dy/64+dx/128)/2`。工具里有**反算自检**。
例：`(+2,−3)` px ⇒ 世界 `(−0.03125, −0.01563)`。

> ⚠ 挪位后几何必然探出瓦片 ⇒ 生成时会**剪裁到 `[0,1]`**（flatiso 铁律）。
> 剪掉的缺口在实机里由**邻格精灵的溢出**盖住（OpenTTD 轨道精灵本来就互相重叠，
> 263px 的格位才装得下 256px 的瓦片）。不剪的话 flatiso 会报 `超出占地`。

### 4.9 补空白：挪之后必须把留下的空白填上（人工裁定）

整体挪位后，几何在一端探出瓦片、另一端留下空白。**绝不能直接剪掉就完事**（那就是“缺一块”）。

| 部件 | 怎么补 |
|---|---|
| 钢轨 / 道砧（连续） | 预位移范围回扩同样的量 ⇒ 位移完正好还铺满 `[0,1]`。侧面效果是纵向那截被抵消 |
| 柕木（周期性） | 位置 = `0.012 + k·间距 + 纵向位移`，只保留落在 `[0.012,0.988]` 的 ⇒ **相位跟着位移走**，末端不够就多铺一根 |

实现在 `tools/gen-g1-switches.mjs` 的 `alongRange()` / `sleeperBoxes()`，
并有 `clipBox()` 计数器：**正常情况下应该是 0 处被剪**。

调试开关（出对照图用，别拿它生成正式模型）：
```
G1_SWITCHES_ZERO=1    node tools/gen-g1-switches.mjs   # 零偏移（= 改动前）
G1_SWITCHES_NOFILL=1  node tools/gen-g1-switches.mjs   # 只挪不补（会留空白）
```

> ⚠ **一个容易误会的几何事实**：屏幕位移 `(dx,dy)` 振开看是“横着挪多少”，实际上分解到**轨道自己的轴**上才是真正生效的部分。
> 例：`X = (+5,−2)` ⇒ **纵向 5.03 px + 横向 0.56 px**。
> 而柕木间距投影到屏幕是 5.82 px ⇒ 纵向那 5 px ≈ **0.86 个间距**，
> 看上去几乎一样。所以“改了但看不出”不一定是没改，而是这个偏移本就大部分沿轨。
> 工具会把每个方向的 纵向/横向 分量打印出来。

> ⚠ 这几个数还在收敛中：`probe_track_x#1` 目前是 `(+1,−1)` 而 `#3` 是 `(0,0)`，
> 两者都是 `TRACK_Y`，但 `#1` 引擎不用（`RTO_Y` 取 v3）。**收敛后只改那张表重跑。**

### 4.10 坡道：抬升量、基准朝向、以及**取图顺序不是顺序贴**

**抬升量**（实测参照包，不是推的）：
`test-pre_01` 内容高 129 px（平轨），`test-pre_up` 161 px ⇒ 一格坡抬 **32 px @4x**。
换算成 flatiso 的 z：`32 / 156.7673 = **0.2041 格**`。
反查一致：OpenTTD 坡抬 8/16 = 0.5，而 flatiso 竖轴是它的 2.4495 倍 ⇒ `0.5/2.4495 = 0.2041` ✓

**基准朝向**：`SLOPE_NE` = N 角与 E 角同时抬起。由角映射 N=(0,0)、E=(0,1)
⇒ 抬的就是 **x=0 那条边**。它的轨道是 `TRACK_X`（沿 x），正好垂直于抬边 ⇒ 顺坡走 ✓
于是基准模型写成 `z(x) = 0.2041·(1−x)`。

**取图顺序（坑）**：flatiso 的"朝向"是**绕占地中心旋转模型**
（`flatiso/core/raster.mjs:19-42`），90° 那一步是 `(x,y) → (1−y, x)`。
⇒ `view k` 把 view0 里位于角 C 的特征搬到 `R^(−k)(C)`，`R` 就是引擎的四重旋转（北→东→南→西）。
view0 抬的是 N–E 边，于是：

| view | 抬起的边 | ≈屏幕 | 对应槽位 |
|---|---|---|---|
| v0 | x=0（N–E） | 右上 | `RTO_SLOPE_NE` |
| v1 | y=0（N–W） | 左上 | `RTO_SLOPE_NW` |
| v2 | x=1（S–W） | 左下 | `RTO_SLOPE_SW` |
| v3 | y=1（S–E） | 右下 | `RTO_SLOPE_SE` |

而**引擎的槽位顺序是 `NE / SE / SW / NW`**（`rail.h:80-83`）
⇒ 喂图是 `v0, v3, v2, v1`，**槽 7 要 v3、槽 8 要 v2**，不是顺序贴。

> **怎么自查**：别靠眼睛看"哪头高"。屏幕 y = `64(x+y) − 156.7673·z`，
> z 高和"靠后"**都会让像素往上跑**，两者会互相抵消，肉眼看反。
> 直接把四个 view 的**最高像素坐标**算出来对：以瓦片原点为基准，
> 预测 `v0=(41,−11.6)  v1=(−41,−11.6)  v2=(41,20)  v3=(−41,20)`，
> 实渲量到 `(40,−13) (−43,−11) (38,20) (−37,20)` ✓（量法见 `out/slope-dir.mjs`）

### 4.11 ★ 斜向链：半格轨是**切角轨**，不是"斜轨被切一半"（2026-10-03 实机返工）

**先把拓扑背下来**：OpenTTD 的轨道片连的是**瓦片边的中点**，不是角。

| track | 世界坐标线段 | 屏幕形态 |
|---|---|---|
| `TRACK_X` | `(0,0.5) ↔ (1,0.5)` | 斜 `/` |
| `TRACK_Y` | `(0.5,0) ↔ (0.5,1)` | 斜 `\` |
| `TRACK_UPPER` | `(0,0.5) ↔ (0.5,0)` | **水平**（瓦片上半） |
| `TRACK_LOWER` | `(1,0.5) ↔ (0.5,1)` | **水平**（瓦片下半） |
| `TRACK_LEFT` | `(0.5,0) ↔ (1,0.5)` | **竖直**（瓦片左半） |
| `TRACK_RIGHT` | `(0,0.5) ↔ (0.5,1)` | **竖直**（瓦片右半） |

⇒ **屏幕上水平 / 竖直的"斜向直轨"没有整格片**，它只能是**半格轨交替**拼出来的：

| 那条世界直线 | 屏幕形态 | 瓦片序列（轨位交替） | 瓦片原点的屏幕偏移 @4x |
|---|---|---|---|
| `y − x = −0.5` | 竖直 | `(0,0)LEFT → (1,0)RIGHT → (1,1)LEFT → (2,1)RIGHT …` | `0 → (−128,+64) → (0,+128) → (−128,+192)` |
| `x + y = 0.5` | 水平 | `(0,0)UPPER → (−1,0)LOWER → (−1,1)UPPER …` | `0 → (+128,−64) → (+256,0)` |

⚠ 这条链的瓦片是**斜着走**的（东一格、南一格交替），不是沿一条轴直着排。
按"每格都往东"去摆会整体错开 128 px（第一次拼验证图就是这么错的）。

**由此踩的三个坑**（都是实机截图报上来的）：

1. **板 = 板带 ∩ 瓦片**，而且**要沿轨道方向铺满整格再裁** —— 端部必须由**瓦片边**切出来。
   实测形状在屏幕上是一个"左右竖直、上下 2:1 斜切"的**梯形**；相邻两格正好共用那条斜边
   ⇒ 拼起来无缝；而且**整块都在瓦片内** ⇒ 不会被邻格精灵盖掉。
   **三条弯路，都别走**：
   - 板带里留中央排水沟（`y ∈ [0.48,0.52]` 下凹）⇒ 板被纵向切成两条窄带，两条带在瓦片里的
     位置不同、被瓦片边裁掉的长度也不同 ⇒ "板缺半截、一根钢轨短一截"。
   - 只取局部 `x ∈ [0,1]`（= 理想矩形，端部沿 `x±y = const` **垂直**切）⇒ 那个矩形的两个角
     落在瓦片外（`y<0` / `x>1`，各 0.09 格）。**出瓦片的部分会被邻格精灵盖掉**
     （引擎按瓦片从远到近画，后画的盖先画的）⇒ 实机里只剩中间一个矩形，接缝处露白。
   - 把理想矩形整块发出去（`emitDiag` 不裁）：同理，溢出的角照样被盖，比上一条还差，
     而且会多一条 flatiso 的"超出占地"警告。
   ⇒ **正解是反着来**：让几何**比瓦片长**（`emitDiag` 里给"沿轨全长"的件把局部 x 从
     `[0,1]` 放到 `[-1,2]`），再交给 `clipTile` 去切。
     **扣件座不延长** —— 它是离散小块，局部 x 本来就按整格排好，延长会变成一条长条
     （模型里用 `long: true` 区分这两类）。
   > 判据：拼一条斜向链，两块板之间应当**共用一条 2:1 的斜边**（不是缺口、不是错位），
   > 两侧边连成一条直线，钢轨 / 第三轨连续且第三轨始终同侧。
2. **第三轨会左右交错**。引擎给这条链的槽位是 `RTO_W←v1` 与 `RTO_E←v3` —— 同一模型
   **相差 180°** ⇒ 第三轨必然被甩到直线两侧。
   修法：再做一个**关于板带中心 `y = 0.5` 镜像**的模型，接给 `RTO_S` / `RTO_E`
   （`180°` 旋转把镜像翻回来 ⇒ 与 `v0` / `v1` 同侧）。板与钢轨本来就对称 ⇒ 逐字相同。
   ⚠ 新模型名要**排在本表所有模型名之后**（`atlas.mjs` 按模型名排序给格位），
   否则新精灵挤进来，整表 rect 全变。
3. **overlay 不能带第三轨**。道岔瓦片上引擎按轨位**逐段**叠加 overlay
   （三向要叠 3 张）⇒ 会同时出现三套第三轨互相穿插。`track_overlay` 只留钢轨 + 扣件座，
   与 G1 一致；这也正是现实里道岔处接触轨必须断开的做法。

**交叉口（`RTO_CROSSING_XY`）**：两条第三轨都要在**对方轨道占的板带**处断开成两段
（断口 = `[BAND[0], BAND[1]]`，宽 0.36）。只断一条的话，另一条会从对面两根钢轨底下穿过去，
图形对不上，道理上也是短路。

### 4.12 隧道洞门：暗幕的位置、山坡侧壁、以及**分层要跟着"接缝"走**

TUN-5（地铁矩形洞门）实机返工多轮（人工 2026-10-03 / 10-04：「地铁的隧道图像没有侧边，
柱子不完全是左右排列，黑幕位置靠后」→「侧面应该是一个三角形，黑幕太靠前了，
洞口柱的侧面也有问题，洞口柱子还断成两截了」→「和洞口（也就是洞顶下沿）同高」）：

> 分层那两条（下面第 3、4 条）**为什么会错**记在 `docs/踩坑.md` 的 **A7**（引擎分层）
> 与 **D4**（先认准是哪一块再动手）；这里只写"该怎么做"。

1. **暗幕（洞里那块黑）的位置**：不要贴到洞口面上（看着"太靠前"），也不要往山里放太多。
   等距下**横向位移比竖向敏感得多** —— 往里挪一点点，屏幕上就横移一大截，整块会从洞口
   一侧**露出去**，洞里就变成"一边黑、一边露出灰色内壁"，连洞口那两根柱子看着都不对称了。
   正确的落点是：**往里退一小段，露出的两侧正好落在洞口内壁的屏幕宽度之内** ——
   内壁会替你挡住它。现在取"从洞口面往里退 0.08 格"（`TU.BORE_X`）；数值本身会随洞口
   宽度/端墙厚度调，判据是上面那句。
   - 另外暗幕的 **z 要从道床顶面起**，别从地面起 —— 否则会切进道床和钢轨。
2. **仰面（山坡）的两条侧边要补侧壁**，而且必须是**三角形**（人工 10-04）。
   仰面是张梯形土坡，坡面本身**悬在地面之上**；y 方向那两条边原来是**空的**，
   从侧面看就是"一张土纸贴在山体上"（人工 10-03：「没有侧边」）。
   - 三角 = 端墙那一侧的竖边（由端墙端面收口）+ 坡面边缘 + 落到地面。
   - **不要补矩形** —— 那会和翼墙的三角面叠在一起（人工 10-04：「侧面应该是一个三角形」）。
   - ⚠ flatiso 的 `quad` 只认 4 点 ⇒ 三角形**末点重复**（同 `wing5` 的写法）。
3. ★ **洞门的上下两半都要过 `split5`（沿 `y` 左右分半）**。这是"柱子断成两截"的根因：
   原来柱脚（`portalLow5`）整块塞在 `tunnels:` 里，而柱身**近半**在 `tunnel_overlay:` 里
   ⇒ 靠近镜头那根柱子被劈成两半（下半在底图、上半在 sortable 层），中间还夹着引擎插进去的
   那层覆盖物 ⇒ 实机里就是"柱子断成两截"、柱侧面也对不上。
   ⇒ 两个函数**都**过 `split5`，A 组拿 `lo`、B 组拿 `hi`，保证**一根柱子整根在同一层**。

4. **分层口径（定稿）：柱子按左右分半，但"与洞口上沿同高"的那一小段整块进 overlay**
   （人工 2026-10-04：「和洞口（也就是洞顶下沿，不是洞顶上沿）同高」）。

   把洞门沿**高度**切成三段，段界一律取生成器里**已有的口径常量**（地面 / 起拱线 /
   洞口净高 / 板顶），**不要写死数值** —— 这样改洞口尺寸时三段跟着一起走：

   | 段 | 函数 | z 界 | 层 |
   |---|---|---|---|
   | 柱脚 | `portalLow5()` | 地面 ~ 起拱线 | 沿 `y` 左右分半 |
   | 柱身 | `portalHigh5({ z1: OH })` | 起拱线 ~ **洞口上沿** | 沿 `y` 左右分半 |
   | **柱顶那一小段** | `portalHigh5({ z0: OH })` | **洞口上沿 ~ 板顶（＝过梁那一层高）** | **整块进 overlay，不分左右** |
   | 檐口压顶 + 仰面 | `always5()` | 板顶以上 | overlay |
   | 过梁 | `lintel5()` | 洞口上沿 ~ 板顶 | overlay |

   为什么单切这一段：**过梁本来就占"洞口上沿 ~ 板顶"这一层高、而且它在 overlay**；
   柱子同一高度那段若留在底图，会被引擎后画的那层覆盖物压掉 ⇒ 实机里柱子与过梁之间
   裂开一道缝。⇒ **判据是"切分线要对齐过梁的下沿"**，而不是自己拍一个高度。
   ⚠ **别把整根柱子搬进 overlay**（试过两次都被否）—— 那会把一根柱子劈成上下两截。

   `portalHigh5({ z0, z1 })` 的参数化就是为这条服务的：默认值等于原来那一段，
   **不传参时几何与从前逐字相同**。

   > 分层自查法：把 `gfx/tunnel5.png` 里 `G4_tunnel5#0`（tunnels:）和
   > `G4_tunnel5_over#0`（overlay）**并排放大看** —— 你要的那块如果只在左边那张里，
   > 就说明它在底图。⚠ 索引图是**纯精灵**、看不到引擎后画的草地覆盖 ⇒
   > "索引图上完整"≠"实机完整"。

> 这四条都是**通用**的：任何"洞口 + 盖土"造型都适用（TUN-1 / TUN-2 若要改，
> 先看 `tools/gen-g1-tunnel.mjs` 里对应的常量，别只改一边）。

## 5. 材质与颗粒

- **`GRAIN_SCALE` 是"世界单位下的格子尺寸"**，不是强度。1 个输出 px ≈ 0.0070 世界单位
  ⇒ 想要 ~1.4 px 的颗粒，取值 **0.010**。早期填 0.7 得到 100 px 的大色块。
- `GRAIN_AMOUNT` 是**材质自身幅度的倍数**（`gravel` 幅度 0.060）。
- 平面着色（flat shading）**没有贴图** ⇒ 想加细节只能加面。所以"加面数"之前先分清
  要加的是哪一层的面，否则只是白烧面数。
- 轨枕分段用**几乎同色**的 `wood_dark`(122,85,48) / `wood_seam`(133,95,49)；
  用 `wood`(169,121,63) 会把接缝衬得像断成三截。
- 钢轨：顶面 `metal`、侧面 `rust`（黄锈）。
- ★ **中性灰要"故意写冷"**（2026-10-03，地铁整体道床返工两次才查清）：光照 + `stylized` 预设会把
  表面往**暖**里带 —— 实测基准 `(160,160,160)` 渲出来的顶面是 **(155,150,142)**（R−B 偏了 13，
  看着发黄）。各通道系数约 **R×1.006 / G×0.969 / B×0.913**。所以要"实机看着是中性的 160 灰"，
  基准得写成偏冷的 **(159,165,175)**（实测渲出来 (157,159,162) ✓）。
  ⇒ **别直接照着想要的像素值填基准色**；用上面的系数反推一版，渲完再采一次像素对。
  （为此在 `tools/flatiso/core/materials.mjs` 加了一个色 `concrete_mid`，见 `VENDORED.md` 的登记。）

## 7. 工作法（可复用）

### 7.1 「生成器写在 `out/`，`.model` 只放字面量」

flatiso 的铁律是**模型是手写字面量，不是生成器**。但手算 84 个 quad 的坐标不现实。

**做法**：临时 Node 脚本（写在 `out/`，gitignore 的）算出所有坐标，**一次性打印成
完整的 `.model` 文本**写入 `models/`。结果是：

- `models/*.model` 里**只有字面量** ✓ 铁律满足
- 坐标由程序算，不会手抄错 ✓
- 参数（带宽、枕木长、轨距、分段数）留在脚本里，**改一个数就能整版重算** ✓
  —— 本轮"道床 0.48 → 0.34 → 0.30"和"横断面 ×1/√2"全靠这个迭代得动

### 7.2 三个诊断图

| 图 | 命令 | 看什么 |
|---|---|---|
| `out/calibrate/anchors.png` | `make diag` | 洋红十字=瓦片菱形、绿十字=瓦片中心压在每个 模型×朝向 上 ⇒ **摆没摆对** |
| `out/calibrate/compare.png` / `compare_zoom_*.png` | `make diag` | 参照包 / xUSSR×4 / 我方 / 叠加，同一锚点 ⇒ **像不像**（量宽窄必须用 zoom 版） |
| `out/calibrate/index.png` | `make sprites` | **偏移索引图**：每个 模型×朝向 一格，全画在同一瓦片锚点上。格内：洋红菱形=瓦片轮廓、**黄十字 + 每 8px 刻度 = 瓦片原点**、蓝格=每 16px（64px 标数）、左上角青点数=朝向号+1；格下三行直写着 `模型#朝向` / `xrel,yrel` 与 **templates.pnml 行号** / `rect`，手调过的行标 `*TUNED*` ⇒ **查名字 + 直接调偏移** |

三个都在 `out/`，**`make clean` 会删掉**，用时重建。
索引图默认 2 倍，改 ±1~2 px 时用 `node tools/sprites.mjs --sheet --zoom 3` 更清楚。
图里的字是 `tools/font5x7.mjs` 里手搓的 5×7 点阵字体（只有大写 + 数字 + 少量符号），
所以标注一律大写、不含中文。

### 7.3 摆放与对账

- 摆放事实在**手写**的 `src/rails/templates.pnml`（人工裁定 O2，无生成器）。
- 手调某一行 ⇒ 在行尾注释写 **`【手调】`**，`make check` 就不再把那行当漂移报。

#### ★★ 新规矩（人工裁定 2026-09，2026-10 修订）：`templates.pnml` 完全归人管，脚本一律不准写它

| # | 规矩 |
|---|---|
| 1 | **任何构建步骤都不准写 `templates.pnml`** —— `make` / `tools/*.mjs` 只读它 |
| 2 | **唯一允许改它的情形**：**新增/删除精灵类型**（增删 `.model`）或**改了分表**（§7.9） |
| 3 | 其余一切改动（几何、偏移、高度、材质…）**只改模型**，不许动模板 |
| 4 | 真要改时，**人工手抄** —— 跑 `make sprites` 拿当前正确值，照着改 `templates.pnml`。**没有任何同步脚本**，`sync-templates.mjs` 已废弃并从 `Makefile` 删除（2026-10-01），原因见下 |

> **为什么把 `sync-templates` 删掉**（2026-10-01）：它按"增量"保留手调（旧值 − 旧基准，
> 再加到新基准上），本意是好的，但**只要基准被污染一次就会滚雪球**——
> 历史上出现过遗留的手调增量被当成基准、rect 写坏，`nmlc` 直接报
> `Read beyond bounds of image file`。而且它是"脚本批量静默改源文件"的典型，
> 与 L4 冲突。现在只保留 `make sprites` 这个**只读**的对账工具。

**为什么这条规矩成立**：flatiso 的图集**只在「该表内的模型数量/顺序」变化时重排**。
只改模型几何 —— **哪怕大幅改高度** —— `rect` 一个都不会变。已实测两次：

- `9901c13` 道床基准 z 0.0020→0.0005（5 个模型整体降高度）⇒ `rect` 全不变
- 本次把**所有枕木 z 0.0040→0.0100**（厚度减 60%）⇒ `rect` 全不变

> ⚠ **2026-10 补正**：上面这条只在**同一张表内**成立。跨表就会连锁 —— 见 §7.9。
>   在分表之前，加一个 0.57 格高的隧道口曾把**同表 40 张轨道图**的格位从
>   263×151 撑到 263×218，`rect` 与 `yrel` 全部失效。

**偏移写在哪，按「一张模板管几个方向」分**：

| 精灵 | 一张模板管几个方向 | 偏移写在 |
|---|---|---|
| `probe_track_x` / `probe_half_upper` / `G1_rail_straight` / `G1_rail_halftrack` | **1 个** | `templates.pnml`（Sprite Aligner 手调，那是人的活） |
| `G1_crossing` / `G1_junction3` / `G1_junction4` | **多个** | **模型几何**（`tools/gen-g1-switches.mjs` 的 `DIR_DELTA`），模板**留基准 `-131,-19`** |

> ⚠ 两边都写 = 双重应用 ⇒ 表现是"**每修正一次就多偏一份**"（踩过，见 `9747e19`）。
> ⚠ 只改多方向精灵、不同步单方向精灵 ⇒ 表现是"**接缝处道床有缝、钢轨连着**"。
>   但**同步也必须在模型侧做**（改 `DIR_DELTA`），不准去改模板。

### 7.4 工具链的硬约束

| 约束 | 说明 |
|---|---|
| `nmlc` 不自带预处理器 | `#include` / `#define` 必须先过 `gcc -E -x c -I.` |
| `quad` 要 **12 个空格分隔的数** | `poly` / `prism` 收的是 `x,y` 点对，别搞混 |
| `poly` **不支持 `\` 续行** | 必须写成一整行 |
| `models/` 必须**平铺** | `listModelFiles()` 不递归；几何组用文件名前缀（`G1_*`） |
| 改 railtype 后**必须** `make check` | railtype 错了编译零报错，游戏里表现为"车库里一辆车都没有" |

### 7.5 判编码：以字节为准，别信终端

`Get-Content` 在 PowerShell 5.1 下按 **ANSI 码页**读 UTF-8 文件，**必然**把中文显示成
乱码（`鈥斺€?`）。本轮据此误判过一次"文件坏了"，其实文件完好。
**一律用 `node -e` 或 `make check` 复核**，`make check` 有编码自检。

### 7.9 ★ 图集按类分表 + 模板参数化（人工裁定 2026-10）

**两条一起定的：**

1. **不同种类的组件各自出一张 PNG** —— 轨道 / 隧道口 / 接触网 / 栏杆 …… 各一张。
2. **模板取哪张图，用 NML 自带的模板参数**（不是 `#define` 宏）。

#### 为什么要分表（不是"想分就分"）

flatiso 的打包键**只有占地**（`core/atlas.mjs:16,25` `fpKey(it.footprint)`），
而且格位尺寸取**组内极值统一**（`atlas.mjs:37-47`）。于是：

> 加一个 0.57 格高的隧道口 ⇒ 同表所有精灵的格位从 **263×151 撑到 263×218**
> ⇒ **40 张轨道图的 `rect` 与 `yrel` 全部失效**（`yrel` 从 −19 变 −86）。

分表之后，**改隧道不会再动轨道表**。

#### 登记表：`tools/sheets.mjs`

```js
{ key: 'rail',   match: /^(probe_|G1_(crossing|junction|rail|track))/ },
{ key: 'tunnel', match: /^G1_tunnel/ },
{ key: 'catenary', match: /^G1_(catenary|pylon|wire)/ },   // 以后
{ key: 'fence',    match: /^G1_(fence|railing)/ },          // 以后
```

- **顺序即优先级**（先匹配者胜）。
- **每个模型必须匹配到一张表**，匹配不到直接**报错**，不许静默丢图。
- **一个类只能有一种占地**：混了会产出多张 PNG，`render.mjs` 直接拦下。真那样就把这个类再拆。

#### 怎么实现（**不改 flatiso**）

`tools/render.mjs` 用 flatiso 现成的 `--models/--out/--only` **按类多跑几遍**，
每遍只喂本类模型 ⇒ 各自算 union frame ⇒ 各自一张 PNG。然后把各遍的
`openttd.json` **合并成一份**（`entry.sheet` 改成本表文件名）。

产出：`gfx/rail.png`、`gfx/tunnel.png`、`gfx/openttd.json`（合并清单）。

#### 模板参数化

```nml
template t_G1_tunnel_stone_v0(sheet) {
  [0, 0, 263, 218, -131, -86, sheet]     // ← 第 7 个字段是形参，不再写死文件名
}
```
调用处传字面量：
```nml
t_G1_tunnel_stone_v0("gfx/tunnel.png")
```

- **实测可行**：nmlc 接受「模板形参直接当文件名」（不然只能像 Neo 那样 `name+"_01_32bpp.png"` 拼接）。
- **新风险**：传错表名**不会报错**，只会静默从错的 PNG 截图。
  ⇒ `tools/check.mjs` 新增核对：调用处传的表名必须 == 该模型实际所在的表。
  **已做反向测试**（故意传错，check 退出码 1）。

#### 改分表 / 增删模型之后

```bash
make sprites        # 打印每个「模型#朝向」在 templates.pnml 的行号、当前值、以及算法值
```

**照着输出人工手抄 `templates.pnml`。没有同步脚本**（`sync-templates.mjs` 已于
2026-10-01 废弃、对应 Makefile 目标已删除，原因见 §7.3 的注）。

`make` 永远不碰 `templates.pnml`；`make sprites` 也只读不写。
有意偏离算法值的行，行尾写 `【手调】`，`make check` 就不再报它。

> **实测收获**：分表把上一次"隧道撑大轨道表"的重排**完全还原**了 ——
> 40 条轨道模板的 `rect` 一个都没变（`rect 变 0`），只加了形参。

## 8. 一次建模的标准流程（照抄）

1. **过 D11 确认门** —— 该组的道床/轨枕/钢轨/隧道口 + C8 四项，人工确认后才动手。
2. 在 `out/` 写一次性生成脚本，参数化（带宽/枕木/轨距/分段）。
3. 生成 `models/G?_xxx.model` → `make sprite` 渲染。
4. `make diag` 看 `anchors.png` 摆位 → 看 `compare_zoom_*.png` 比比例。
5. 比例不对 ⇒ **回 §2 分清是哪个旋钮**，改脚本参数重算，别手改坐标。
6. `make sprites` 核对锚点（模型尺寸一变，锚点就会动），必要时更新 `templates.pnml`。
7. `make` + `make check` 全绿。
8. **实机看** —— 最终判据在游戏里，不在数字上。

### 9.1 三条引擎口径（不背必返工）

1. **导线 28 张，索引 = `WireSpriteOffset`**（`table/elrail_data.h`），
   **不是** `RailCatenarySprite` 的**名字条数 30**。
   取图是 `elrail.cpp:589 AddSortableSpriteToDraw(wire_base + sss.image_offset, …)`，
   而 `_rail_catenary_sprite_data[]` 里存的是前者。
   序：`0/1` 平·1 格跨 X·Y · `2/3` 平·1 格跨斜 · `4–7` 坡·1 格跨 ·
   `8–15` 杆在第一端 · `16–23` 杆在第二端 · `24–27` 洞口/车库口。
2. **支柱 8 张 = 「4 种走向 × 杆立在哪端」**（`PylonSpriteOffset`）。
   模型只画**立在原点的一支杆**，瓦片内偏移由引擎给
   （`_x_ppp_offsets` / `_y_ppp_offsets`）⇒ 支柱模板的 yrel 不是零。
3. **引擎给导线额外抬 `ELRAIL_ELEVATION = 10 单位 = 0.2552 格`，支柱不抬**
   ⇒ **模型里的 z 是"相对引擎原点"的，不是世界高度**
   （我们：接触线写 0.1448 → 游戏里 0.40）。
   上/下坡另有 `ELRAIL_ELEVRAISE = 19` / `ELRAIL_EVLOWER = 9` 单位。

### 9.2 几何手法（可复用）

| 手法 | 怎么做 | 为什么 |
|---|---|---|
| **沿轨坐标** | 斜向用 `s = x+y`（横跨轨向）、`t = x−y`（沿轨）表达，几何与直向**同构**，最后套一层 `(s,t)→(x,y)` | 斜向就是直向转 45°，用 s/t 写可以直接照抄直向公式 |
| **单位形状 × 各自 D** | 形状函数只返回 `0..1`，每根线再乘**自己的**下垂 `D`。半弧 `2q−q²`（2 格跨的一半）、短弧 `4q(1−q)`（1 格跨） | 把常量直接喂进形状函数 ⇒ 两根线永远同深；改 D 只动高度、不动弧度（真实踩过） |
| **吊弦** | 落在两根线**各自的高度之间**；直向 4 根（沿格 0.2/0.4/0.6/0.8）、斜向 3 根（沿半格 0.25/0.5/0.75） | 承力索自己会下垂，吊弦长度必须逐根算 |
| **坡道跟坡面斜** | 沿格加 `RISE = 0.2041`（= 8 单位 = 一层地形高差，与 `gen-g1-slope.mjs` 同源）；上坡 x=1 那头高、下坡 x=0 那头高 | 上一版两端都用低端常量 ⇒ **高的一头整整插进坡里 32 px** |
| **细线线径** | 4x 下：半厚 0.0030 ≈ **0.94 px**（含抗锯齿看到 2~3 px）、0.0045 ≈ 1.4 px（3~4 px）、斜向 t 半宽 0.0100 ≈ 2.6 px（竖直 1 单位 = 157 px、沿轴 1 单位 = 128 px） | 参考包在 1x 只有 1 px 宽，人工要求"做粗一点"；4x 下"看得见"的门槛约半厚 0.003 |
| **斜棒（斜弯臂）** | 手写 **6 个 `quad`**：顶面绕序 `(x0,y0)→(x1,y0)→(x1,y1)→(x0,y1)`（从 +z 看逆时针），底面**反序**，四个侧面 = `[底_i, 底_i+1, 顶_i+1, 顶_i]`。斜向的把 x/y 换成对角线的两个足迹角即可 | `box` 只能轴对齐、`prism` 只能水平挤出、`shed` 是**从地面起**的楔形 ⇒ 悬空的斜杆只能手写面。绕序按 Newell 算，写反 = 整面被剔除（不是变黑） |
| **绕柱标牌** | 标牌做成**环箍**：一个比柱身四周各出 ~0.0025 的 `box`，矮矮一圈 | 一个模型要转 4 个朝向用；薄板只挂柱的一侧时，**转 2 个朝向就会被柱身挡住**，牌子看着"时有时无" |

### 9.3 ⚠ 绕序：斜向那一组必须**整组反过来**

`quad` 不带法线，flatiso 用 Newell 按顶点序算法线，**反了会被背面剔除** ——
不是变黑，是**整根消失**（现象特征：直向导线都在，斜向只剩吊弦）。
`(s,t)→(x,y)` 是**镜像**（det = −2）⇒ 直向那套绕序在斜向法线朝内。

自检手法：写一次性脚本打印每面 Newell 法线，斜向接触线的顶面必须 `nz > 0`。

### 9.4 摆放：模板值 = 算法值 − 引擎原点补偿

引擎按表里的 `(x_offset, y_offset, z_offset)` 当原点，我们按"瓦片原点"算 ⇒ 每族整体偏。

**现行生效值**（2026-10-03 人工实机调过，**一律以 `src/rails/templates.pnml` 的行内数字为准**）：

| 族 | xrel, yrel |
|---|---|
| X 平 / 上坡（v0） | −187, −133 |
| X 下坡（v0） | −187, −101 |
| Y 平 / 上坡（v1） | −75, −133 |
| Y 下坡（v1） | −75, −101 |
| 斜 NS（v0） | −129, −137 |
| 斜 EW（v1） | −75, −164 |
| 支柱 a（v0·v1·v2·v3） | −131,−113 · −11,−173 · −131,−233 · −251,−173 |
| 支柱 b（v0·v1·v2·v3） | −131,−113 · −28,−170 · −131,−233 · −225,−173 |

> `templates.pnml` 头注里那张按 origin 推导的 Δ 表是 **30 槽时代**的，已被实机修正取代 ——
> 别拿它算新值，直接抄同族的现成行。

### 9.5 槽位三坑

1. **口径错**：按 `RailCatenarySprite` 的名字条数（30）排 ⇒ 6 条斜向 + 4 条洞口全错位。
   正确口径 = `WireSpriteOffset`（28）。**判据靠实机**：让作者报"第几号槽的线跑到哪去了"，
   再逐条对源码。
2. **斜向只有 6 张**（2/3/10/11/18/19）：LEFT/RIGHT（UPPER/LOWER）**共用同一张精灵**，
   引擎靠包络盒 origin `(8,0)`/`(0,8)` 自己挪半格 ⇒ **斜向模型必须画在瓦片正中**
   （`t = x−y = 0`），模板 **x 不补偿**。
   画成"贴着 W 角"⇒ 半格位移被叠加两次，实机里跑到另一条半轨上。
3. **每个方向要 3 张**（2 格跨前半 / 后半 / 1 格跨短跨）：`_rail_wires[…][轨道位][几处立杆]`
   的第三维就是"本格有几处立杆"。
   三张都画成同一条整格线 ⇒ 每格自成一条对称弧，**永远接不上隔壁那格**。

### 9.6 「禁用 / 换一张图」的两个小手法

- **禁用某个槽位** ⇒ 指向一张**全透明占位**即可。现在借 `levelcrossing` 表里
  `t_G1_levelcrossing_blank_v0` 的那一格（人工已核 `max alpha = 0`）。
  **NML 允许一个 spriteset 里混多张 PNG**（`sheet` 是每条模板各自的实参）。
  参考包也这么关接触网（JP+：`catenary_wire: sw_fake_track_grass`）。
- ⚠ **不要为了"多一张空图"往图集里插空模型**：atlas 按**模型名排序**打包
  （`tools/flatiso/core/atlas.mjs:31-52`），插进去会把后面所有格位顶移位、`rect` 全废。
  要么借别的表的空格，要么让新名字**排在最后**（追加到尾部，前面格位不动）。
- **32bpp 不能换色**：Action5 / 调色板重映射只作用于 8bpp，换颜色只能**再渲染一份图**
  —— `G1_brown_*` 那套就是这么来的（代价 = 每个模型多一份 + 一套派生模板，
  见 §7.9 与 `美术要素方案.md` §6）。
