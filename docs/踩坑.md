## A. 引擎口径类

### A1. flatiso 的 `xrel/yrel` **不能**直接喂 NML ⚠️

| | |
|---|---|
| **现象** | 1×1 模型只有 view 0 摆放正确，view 1/2/3 整体错位半格（128 px / 64 px） |
| **原因** | `openttd.json` 的 `xrel/yrel` 是相对「**该朝向旋转后占地矩形的西北角**」；OpenTTD 摆放用的是相对「**瓦片原点 = 菱形上顶点**」，它不随精灵内容旋转 |
| **修法** | 用恒定的 `centerAnchor`（占地中心投影，绕占地中心旋转因此不随朝向变）反推：<br>`原点像素 = centerAnchor − ((cy−cx)·HW, (cx+cy)·HH)`<br>`xrel = −原点像素x`，`yrel = −原点像素y` |
| **已挡** | ✅ `tools/util.mjs` 的 `anchorToXrelYrel()`；`tools/sprites.mjs` / `calibrate.mjs` / `compare.mjs` 都走它 |

### A2. flatiso 的 90° 步进是 OpenTTD 旋转的**逆** ⚠️

| | |
|---|---|
| **现象** | 直线轨的 X/Y 分不清，半格轨的四个方向全错 |
| **原因** | 实测：`flatiso view k ≡ R^(−k)`，`R` 是 OpenTTD 的四重旋转（`X→Y`、`UPPER→RIGHT→LOWER→LEFT`） |
| **修法** | 槽位取图对照表：`X→v0`、`Y→v3`、`UPPER→v0`、`LOWER→v2`、`RIGHT→v3`、`LEFT→v1` |
| **已挡** | ✅ 表写在 `src/rails/railsprite.pnml` 顶部注释；实测数据在 `定标.md` §4 |

### A3. 半格轨的道砟是**板带**，不是「角三角」 ⚠️

| | |
|---|---|
| **现象** | `TRACK_UPPER` 渲染成一个**又高又窄的尖帽子**，凸在瓦片上顶点上方 |
| **原因** | 我按「瓦片角上的三角形」建模了。实测参照 `04_32bpp.png#0` = `x[-87,93] y[14,46]`，反推出道砟其实是**沿轨道的板带** `x+y ∈ [0.26, 0.74]` |
| **修法** | 直线与半格轨**同一条板带规则**，只是直线用 `y` 坐标、半格轨用 `x+y` 坐标 |
| **已挡** | ✅ `定标.md` §2.5 有完整规则表 |

### A4. OpenTTD 的竖轴是**压缩的**，flatiso 是真正交 ⚠️

| | |
|---|---|
| **事实** | OpenTTD：`pt.y = (y + x − z)`，`TILE_SIZE = 16`、`TILE_HEIGHT = 8` ⇒ 一个瓦片边长画 32 px、一个高度级画 8 px，比值 **0.25**。<br>flatiso：真正交 30° 相机，`zPx = HW·√6/2 = 156.7673`（= 0.866 × 181），同一个高度级画 **78 px** |
| **后果** | **同一个 z，flatiso 画出来是 OpenTTD 的 2.45 倍。** |
| **修法** | 凡是**要和引擎地形 / 车辆 / 别的 GRF 对齐**的东西，**宁矮勿高**。建筑类可以不管（纯美术约定），轨道类必须管 |
| **已挡** | ⚠️ 没挡，靠人记住。见 A5 |

### A5. **不要抬高地基**（人工裁定 2026-09）⚠️

| | |
|---|---|
| **现象** | 道床做成凸起的台子后，跨瓦片绘制时被邻格精灵遮挡 → **图形错位** |
| **原因** | OpenTTD 按画家算法逐瓦片绘制，瓦片内抬高的几何没有跨瓦片的 z 保证；再叠加 A4 的 2.45 倍放大，凸起会更明显 |
| **修法** | 道床**贴地**（`z = 0.002`），把高度全部给轨枕（0.011）和钢轨（0.013）。参照图实测也只有 2~3 px 的微凸 |
| **已挡** | ✅ 写进 `probe_track_x.model` / `probe_half_upper.model` 的文件头；`定标.md` §2.5 |

### A6.1 ★★ 半之第二：**局部 id 不能撞车** ⚠️⚠️

| | |
|---|---|
| **现象** | 某个 railtype item 的属性**打在了另一条轨道身上**，那条轨道行为怪、被顶掉的那条等于没定义 |
| **原因** | `newgrf_act0_railtypes.cpp` 的 **reservation 阶段**（`RailTypeReserveInfo`，第 208-220 行）：<br>`case 0x08: rt = GetRailTypeByLabel(label); if (无效) rt = AllocateRailType(label); type_map[id] = rt;`<br>**Action 0 的 ID 是本 GRF 的「局部 id」，标签决定它指向哪条真轨道**。<br>两个块用同一个局部 id ⇒ reserve 阶段按顺序覆盖 `type_map[id]`，**只有最后那个生效** |
| **旁证（自证）** | `nmlc --nfo` 里能直接看到两个块带同一个 `\wx????` id |
| **修法** | **所有 railtype 都给显式且不重复的 id**。当前分配（人工裁定 2026-10-02）：<br>**0~6 归隐藏兼容类型**（`SACN` `SACA` `SACD` `BACN` `BACA` …，见 A6 的废止说明）；<br>**7 起归可见轨道**（`SADN`=7 `SBDN`=8 `SCDN`=9 `SBDA`=10 `SCDA`=11 `SBEd`=12 `SBDD`=13）；<br>内建 `RAIL`/`ELRL` **不再占用** id 0/1（因为不再覆盖它们） |
| **已挡** | ✅ `tools/check.mjs` 第 1 项自检就是"局部 id 互不重复"，**这条真的抓到过**（2026-10-02：`SACD` vs `SADN`、`BACN` vs `SBDN`、`BACA` vs `SCDN`） |
| **自检** | `nmlc --nfo=…` 后，**每个 `00 10` 块的 `\wx????` id 必须互不相同** |

> **任何 railtype 改动后都要跑 `make check`** —— 它专门查这个，
> 而 nmlc 本身**不报错**（同 id 的块会被并掉，`Railtype items: n/64` 的计数是唯一预警）。

### A7. `tunnels:` 与 `tunnel_overlay:` 之间**隔着引擎画的一层覆盖物** ⚠️⚠️

| | |
|---|---|
| **现象** | 明明画了的东西，实机里却"少半截"—— 例如洞门那根柱子只剩底下一段、柱子与上面的过梁之间裂着一道缝。**但同一张精灵在索引图上完整无缺** |
| **原因** | 定义了 `tunnel_overlay:` 之后，引擎的绘制顺序是：草地底 → **`tunnels:`** → 车 → **一层草地覆盖** → **`tunnel_overlay:`**。`tunnels:` 里画的东西会被中间那层覆盖物压掉一部分，只有 `tunnel_overlay:` 才画在最后。而**索引图是纯精灵、根本没有这层覆盖物**，所以"图上完整"≠"实机完整" |
| **修法** | 两条判据：<br>① **凡在屏幕上彼此相接的部件，必须放在同一层** —— 从洞口上方横过去的东西（过梁、檐口之类）在 overlay，那么柱子**与它相接的那一段**也得进 overlay，否则接缝正好落在覆盖物那一层上，被切开；<br>② 切分线要**对齐某一层已有的边界**（比如与洞口上沿同高 —— 那正是过梁的下沿），不要自己拍一个高度。对齐之后既不重叠也不留缝，而且洞口尺寸一改，两段跟着一起走 |
| **已挡** | ❌ 工具链挡不住：`check` 只对账"模板 ↔ 图集"的坐标，看不出层次效果；索引图也看不出来。唯一判据是**把同一张表的 underlay 与 overlay 精灵并排放大比对**（手法见 D4），最终仍要实机确认 |

> ⚠ **反面教材：不要用"整块搬层"来修接缝**。把整根柱子搬进 overlay，等于把它劈成上下两截
> （一截留在底图、一截进了 sortable 层，中间照样夹着那层覆盖物）—— 试过两轮都被否。
> 正确做法是按**接缝在哪里**切，而不是按"哪个部件"整体搬。

### A8. `tunnel_overlay:` 的模板偏移**和底图不是同一套** ⚠️

| | |
|---|---|
| **现象** | 洞口的上半（过梁 / 檐口 / 山坡那些"遮在车前面"的东西）整块**掉到洞口下面去**，或者悬在半空、跟下半对不上；而底图那一半是对的 |
| **原因** | `make check` 是拿 `centerAnchor` 反推 `xrel/yrel` 的，**同一张表里所有精灵都会算出同一个值**。但引擎画 `tunnel_overlay:` 那张 sortable sprite 时用的原点，**跟画 `tunnels:` 底图时不是同一个** —— overlay 的 `yrel` 必须比算出来的值**再往上挪一大截**（量级跟洞门高度同阶）。一条模板只能填一套偏移，这个差别**补不进几何里**，只能手调模板 |
| **修法** | 照**已经实机验证过的 G1 隧道**那一对模板抄关系：`t_G1_tunnel_stone_*`（底图）与 `t_G1_tunnel_stone_over_*`（overlay）的 `yrel` 之间有一截固定差，**那一截就是 overlay 的额外偏移**。给新洞口套上同样的关系，并在这些行注释里标 `【手调】`（`check` 就不再报）<br>⚠ **别把 overlay 的 `yrel` "修"回计算值** —— 那正是把洞口上半按到地下去 |
| **已挡** | ❌ `check` 只会说"与 centerAnchor 不一致"，它不知道 overlay 另有原点 ⇒ 靠 `【手调】` 标记 + 这条记录。判据：**同一张表里"底图那一组"和"overlay 那一组"的 `yrel` 之间应该有一截固定差**，两组都该标 `【手调】` |

> 这条是 2026-10-04 收尾时反查出来的：TUN-5 的 `_over` 四条里，有一条当年被改对了、
> 另外三条还留在底图那套偏移上 —— 人工手改统一之后才发现**它和 G1 的规律完全一致**。
> ⇒ 以后遇到"overlay 整体错位"，先去看 G1 那对模板的差值，而不是去改几何。

## B. flatiso 建模类

### B1. **平面着色 ⇒ 共面的面加多少都一样** ⚠️

| | |
|---|---|
| **现象** | 把道砟顶面切成 200 个小四边形，看起来和 1 个四边形**逐像素完全一样** |
| **原因** | flatiso 是 **flat shading**、没有贴图。同法线的面拿到同一个颜色 |
| **修法** | 「提高面数模拟不规则表面」的正确说法是 **「提高『法线朝向不同』的面数」** —— 要起伏的、倾斜的小面，不是把平面切碎 |
| **已挡** | ✅ `定标.md` §2.6 |

### B2. 贴地想要「颗粒感」怎么办 —— **主要靠 grain，不是靠几何**

| | |
|---|---|
| **做法** | ① **grain（逐像素，不占面数）**承担细颗粒；② 道床用**细密的倾斜小面**只承担大尺度起伏与光照差；③ 材质**统一**，别用不同材质制造色差 |
| **别做** | 别靠「大块面 + 不同材质」做碎石 —— 平面着色下**面有多大色块就有多大**，出来是迷彩块（人工反馈过两次） |
| **已挡** | ✅ 两个 probe 模型就是这个配方 |

### B2.1 ⚠ `--grain-scale` 是**世界单位下的胞元边长**，不是倍率

| | |
|---|---|
| **现象** | `GRAIN_SCALE = 0.7` → 道床是一片 **100 px 大的软斑**，完全没有颗粒 |
| **原因** | `core/grain.mjs`：`scale: o.scale ?? 0.0072`，注释写明「**1 个输出像素约等于 0.0070 世界单位**」；`build.mjs` 是**直接赋值** `scale = Number(args['grain-scale'])`，不是乘 |
| **修法** | 想要 1~2 px 的碎石粒 → **`GRAIN_SCALE = 0.007 ~ 0.014`**。当前用 `0.010`（≈1.4 px） |
| **顺带** | `GRAIN_AMOUNT` 才是倍率（乘在材质自带幅度上；`gravel` 自带 `0.060`）。当前 `3.0` ⇒ ±18% |

### B3. `poly` **不支持 `\` 续行** ⚠️

| | |
|---|---|
| **现象** | `poly 0.002 gravel 0.0,0.3 \` + 下一行 → 报 `✗ 坐标要写成 x,y，得到「\」` |
| **原因** | `poly` 的解析器一路吃到「含 `=` 的 token」为止，`\` 被当成坐标 |
| **修法** | **`poly` 的顶点必须写成一整行**（哪怕很长）。`prism` / `quad` 本来就是单行，不受影响 |

### B4. `prism` / `quad` 只吃**一个**材质

| | |
|---|---|
| **现象** | 想给钢轨「顶面金属、侧面黄锈」，`prism` 做不到 |
| **原因** | `model.mjs` 里只有 `box` 支持 `top=` / `bottom=`（`gable`/`shed` 支持 `side=`/`bottom=`）；`prism`、`quad`、`poly` 都是单个材质字符串 |
| **修法** | 直线轨用 `box ... rust top=metal`（四个侧面用基材质，x=0/x=1 两个端面在瓦片边界上被邻格盖住，无所谓）；<br>斜轨没法用 `box`，只能自己拆成 5 个 `quad`：顶面 `poly`(metal) + 2 侧面 `quad`(rust) + 2 端面 `quad`(rust) |
| **已挡** | ✅ `probe_half_upper.model` 里有现成的五面体写法可抄 |

### B5. `models/` 必须**平铺**

| | |
|---|---|
| **现象** | 把模型放进 `models/G1/` 子目录后，`flatiso` 一个都找不到 |
| **原因** | `core/bake.mjs` 的 `listModelFiles()` 不递归 |
| **修法** | 几何组用**文件名前缀**区分（`probe_*` / `G1_*` / `G2_*` …） |

### B6. `prism` 顶点顺序

`prism` / `poly` 的 XY 多边形按「**先 +x 再 +y**」的顺序给（即 `cross_z > 0`），侧面法线才朝外。
顶面/底面法线由 `addPrism` 显式给定，不受影响。

### B7. `quad` 收 **12 个空格分隔的数字**，`poly` / `prism` 才收 `x,y` 对 ⚠️

| | |
|---|---|
| **现象** | `quad 0.064,0.256 0.005  0.096,0.224 0.007 …` → 报 `顶点坐标 需要数字，得到「0.064,0.256」` |
| **原因** | `model.mjs` 里 `case 'quad'` 是 `for (k=0;k<12;k++) a.push(L.num())` —— **12 个独立数字**；`poly` / `prism` 走 `xy(tok)` 解析 `x,y` 对 |
| **修法** | `quad x0 y0 z0  x1 y1 z1  x2 y2 z2  x3 y3 z3  mat`（空格分隔）<br>`poly` / `prism` 保持 `x,y` 对 |
| **已挡** | ❌ 靠人记。写 `quad` 时最容易踩 |

### B8. 用脚本当「计算器」算坐标，再落成字面量

`.model` 里**只能有写死的数字**（铁律 1）。但坐标算术（旋转、裁剪、网格化）
可以**在离线脚本里算好，再把结果贴成字面量** —— 脚本放 `out/`（不入库、`make clean` 会删掉），
只当计算器，不参与构建。

> 本工程的 `probe_track_x` / `probe_half_upper` 的倾斜小面网格与**贴边裁掉的枕木多边形**
> 就是这么算出来的：设计是手定的，脚本只做算术。
> **不要把脚本变成构建的一环**，否则 `.model` 就退化成程序生成了。

### B9. **线脚材质（`*_seam`）不能当一大片面铺** ⚠️

| | |
|---|---|
| **现象** | 人工看 TUN-5 洞门：「**洞门侧面材质有点怪**」。同一堵墙，正面是带颗粒的混凝土，紧挨着的侧面（外端面）却是一块又平、又暗、**没有一点颗粒**的灰 ⇒ 一眼就不像同一堵墙 |
| **原因** | `core/materials.mjs` 的 `GRAIN_RULES` 第一条就是 `[/_seam$/, 0]` —— `*_seam` 一族**颗粒全部归零**。它们的设计用途是给 `strip` / `courses` 画**一条细缝 / 细线**（细线加颗粒只会被糊掉），基色也刻意比基材暗一档。**一条细线的配方铺成一大片面，就只剩一个平色块** |
| **修法** | ① **大面一律用基材**（`concrete_*` / `brick_*` / `tile_*` / `stone_*`…），`*_seam` 只留给真的只有一条线宽的地方。<br>② **同一块体的正/侧/顶面，不要靠"换材质"去分** —— 管线的光照本来就按朝向分：**同一材质**铺在顶面 / 正面 / 侧面上渲出来就是一浅一深（TUN-5 的压顶顶面与端墙正面同为 `concrete_mid`，一亮一暗，可直接对照）。拿两种材质去硬分，分出来的是"两块不同材料"，而不是"同一块材料的两个朝向"——那正是这次"怪"的来源 |
| **已挡** | ❌ 靠人记。**判据：这一片面在屏幕上有没有"一条线"那么窄？** 不是 → 不该用 `*_seam`（这条也一并写进 `docs/建模经验.md` §4.12） |

### B10. **手抄"整块构件"（如 `box()`）时最容易漏掉一个侧面** ⚠️

| | |
|---|---|
| **现象** | 人工：「**洞顶的背面有一条缝**没有面成透明的了」。**正面那几面看完全正常**，一转到背面，洞顶那条棱上就多出一条缝（暗线 / 透明段） |
| **原因** | TUN-1 的压顶是**直接调 `box()`** 的 —— `box()` = **顶面 + 4 个侧面**（只不做底面）。TUN-5 的压顶是**手抄**过来的，只抄了正面 / 顶面 / 两个侧面，**漏了背面（`x = x0`）那一个侧面**。管线又是**背面剔除**的（只画朝向相机的面）⇒ 正面那两个朝向**根本不会画那一面**、看不出任何问题；背面那两个朝向那一条就是**没有面**。 |
| **修法** | 手抄现成的"整块构件"时，**逐面对一遍**："这块是照谁抄的？它有几个面？我写了几个？"**对上就完事**，不要自己重新推导"哪个面看得见"—— 一推导就会按当时的视角把背面判成"反正看不见"。 |
| **查法** | ① **把新旧两版逐像素 diff**，直接看"这次改动到底改了哪一块"（这次就是靠它确认补上的那一面正好落在洞顶背面）；<br>② 扫**封闭透明段**（同一行里被不透明像素夹住的透明像素），**四个朝向逐一扫** —— 只看索引图会漏。 |
| **已挡** | ❌ 靠人记。判据一句：**"我这一块是照谁抄的？它有几个面？"** |

### B11. **精灵在瓦片边界上是「切齐」的 ⇒ 每格接缝一道断口** ⚠️

| | |
|---|---|
| **现象** | 人工：「把**各向铁轨（包括道床）稍微延长出边界一点**，以弥补道床+枕木+铁轨固有高度带来的图像缺损」。把一条链（直向 / 斜向）按引擎的摆法拼起来放大看：**每一格的接缝上钢轨是断的 / 错开一个台阶**，道床边缘也有小缺口；斜向链尤其明显（端面是 2:1 斜切，接缝读起来就是个"Z"字） |
| **原因** | 一块瓦片的精灵**止于瓦片边界**：相邻两格各自把几何裁在同一条世界直线上，那条线上只剩两边的**抗锯齿半透明像素** —— 两块摆回去，缝上就是一条 1px 的暗线；**几何有厚度**（道床+枕木+钢轨叠起来那几个像素）时更明显，因为接缝正好落在有明暗变化的那一段上。轨道又是**唯一必须首尾严格对上**的细线（见 `docs/建模经验.md` §3），错 1px 就看得见。OpenTTD 原版的轨道精灵本来就**互相重叠**，正是为了这个 |
| **修法** | 让几何**沿轨两端各探出瓦片一点**（生成器里 `OVER`），相邻精灵就**叠上** —— 后画的那一张盖住缝。<br>① 只延长"沿轨全长"的部件（板 / 钢轨 / 第三轨 / 罩），**扣件座不延长**（离散小块，延长会变成一条长条）。<br>② 探出量取"刚好盖住 1px 缝 + 一点余量"，**别贪大** —— 探出去的部分在**近端**会被后画的邻格盖掉（引擎按瓦片从远到近画），在**远端**则叠在邻格之上，太大就成了"道床戳进别人家"。<br>③ ⚠ **坡道不延长**：高端再往外延 = 抬得更高（顶大格位 ⇒ 同表全部 rect 跟着重排），低端再往外延 = **穿地**；坡道两端的缝交给**邻格直向件的探出**去盖。 |
| **查法** | **按引擎的摆放口径把链拼出来看**：从 `src/rails/templates.pnml` 取每格的 `rect / xrel / yrel`，按瓦片的屏幕步长摆进一张画布（**远→近**顺序），放大看接缝。<br>⚠ 不要用 flatiso 清单（`gfx/openttd.json`）里的逐朝向 `xrel/yrel` —— 1×1 占地的精灵锚点**逐朝向不变**，清单里那套只有 0° 是对的，照它拼会拼出一堆"孤岛"，白查半天。 |
| **已挡** | 一半：flatiso 现在把**占地当"名义"**（`OVERFLOW_ALLOW`，小幅出界**不报**、真超出才警告），所以"探出边界"是**合法用法**、不会再被判失败；但"哪些件该探、探多少"仍然靠人 |

## C. 工具链类

### C1. `nmlc` **不自带预处理器** ⚠️

| | |
|---|---|
| **现象** | `nmlc china-style-track.nml` → `Illegal character '#' (character code 0x23) at line 7` |
| **原因** | `nmlc` 不认识 `#include` / `#define`。xUSSR 与 China-Set-Tracks 也都是先跑一遍 C 预处理器 |
| **修法** | `gcc -E -x c -I. china-style-track.pnml -o out/china-style-track.nml` 再喂 nmlc |
| **已挡** | ✅ `tools/build.mjs` 的 `compile()`；`Makefile.config` 里的 `CPP` 可换 |

### C2. `gcc` 的 `#include "x"` 先相对**包含它的那个文件**找

`src/rails/railsprite.pnml` 里写 `#include "src/rails/templates.pnml"` 会找不到（会去找 `src/rails/src/rails/…`）。
**修法**：同目录就写 `#include "templates.pnml"`；或者给 gcc 加 `-I.`（本工程两样都做了）。

### C3. nmlc 里 `#` 行标记是**合法**的

`gcc -E` 产生的 `# 0 "file"` 行标记（`#` 后跟空格）nmlc 能吃；但 `#include` 不行。所以不需要 `-P` 去掉行标记，留着还能给出更好的报错位置。

### C4. flatiso 的 `decodePNG` **不处理 8bpp 的 tRNS**，而且 8bpp 精灵压根没有 tRNS ⚠️

| | |
|---|---|
| **现象** | 读 xUSSR 的 8bpp 精灵量 bbox，所有像素 `alpha = 255`，整个格位都被当成"有内容" |
| **原因（第一层）** | 8bpp PNG 的透明是调色板索引 + `tRNS` 块，flatiso 的解码器没展开 |
| **原因（第二层，更阴）** | **实测 xUSSR 的 PNG 里根本没有 `tRNS` 块**（`rail0.png` / `rail1.png` 都是 `8bpp 索引色 + PLTE`，无 tRNS）。透明色是 TTD 经典的 **magic blue `(0,0,255)`**，写死在像素里 |
| **修法** | 用本工程的 `tools/png8.mjs`：`decodePalettePNG()` 解索引色，再 `applyKeyColor()` 把 `(0,0,255)` 刷成透明 |
| **已挡** | ✅ `tools/png8.mjs` + `tools/compare.mjs` 已接 |
| **通用提示** | 拿到任何 8bpp TTD 素材，**先确认它的透明是怎么表达的**（tRNS？magic blue？调色板索引 0？），再谈 bbox / 叠加比对 |

### C5. 反复往同一张 `compare.png` 写会偶发 `UNKNOWN: unknown error, open`

| | |
|---|---|
| **原因** | 文件被占用（图片查看器 / 上一轮的读取没释放） |
| **修法** | 写之前先 `fs.rmSync(file, {force:true})`（`compare.mjs` / `calibrate.mjs` 都已加） |

### C5.1 ⚠ **PowerShell 的 `Get-Content` / `Set-Content` 会搞坏 UTF-8 中文文件**

| | |
|---|---|
| **现象** | 用 `(Get-Content $f -Raw) -replace … \| Set-Content $f -Encoding UTF8` 批量改 `Makefile.config` 后，文件里的中文全变乱码，`FLATISO ?= D:/CNS/ottd/建筑测试/flatiso` 变成 `D:/CNS/ottd/寤虹瓚娴嬭瘯/flatiso`，构建直接找不到 flatiso |
| **原因** | Windows PowerShell 5.1 的 `Get-Content` **默认按系统 ANSI（中文机是 GBK）解码**，读 UTF-8 文件就已经错；`Set-Content -Encoding UTF8` 还会写 BOM |
| **修法** | **改含中文的文本文件一律用 `edit` / `write` 工具**（它们按 UTF-8 处理）。非要用脚本就用 Node 的 `fs.readFileSync(p,'utf8')` + `fs.writeFileSync(p,s)`，别用 PowerShell 的读写 cmdlet |
| **已挡** | ✅ **`make check` 现在自动查这个**（`tools/check.mjs` 的「文本编码自检」）：<br>① 任何 `.json` 必须能解析（乱码后 `JSON.parse` 必抛错）<br>② **源头文件**（`tools/` `src/` `models/` `lang/` `Makefile*`）不许带 UTF-8 BOM —— PS 5.1 的 `Set-Content -Encoding UTF8` 会加 BOM，是最好的指纹<br>③ 源头文件里不许出现乱码指纹字符（`锛銆鈥鐨…`）；`docs/` 与根目录 `.md` 不查，因为本文件就会引用乱码样例<br>④ 外部文件（如 `中国轨道包.csv`）的 BOM 只提示、不报错 |
| **踩了两次** | 第一次是 `Makefile.config`（`FLATISO` 路径变乱码，构建直接找不到 flatiso）；<br>第二次是 `sprite-offsets.json`（中文变乱码 **且 JSON 语法坏掉** ⇒ 表被静默忽略、手调偏移不生效）。<br>**该文件 2026-09 已随 O2 裁定删除** —— 手调现在直接改 `src/rails/templates.pnml`，少一层 JSON 就少一个会坏的地方 |

> **规则**：改含中文的文本文件，一律用 **`edit` / `write` 工具**（按 UTF-8 处理）。
> 非要用脚本，就用 **Node 的 `fs.readFileSync(p,'utf8')` + `fs.writeFileSync(p,s)`**，
> 别用 PowerShell 的 `Get-Content` / `Set-Content`。

### C6. ⚠ **`make clean` 会把定标图一起删掉**

| | |
|---|---|
| **现象** | 刚生成的 `out/calibrate/compare.png`、`anchors.png` 找不到 |
| **原因** | 定标图放在 `out/` 下，而 `make clean` 删整个 `out/`；`make`（默认目标）只跑「渲染 → 模板 → 编译」，**不重建定标图** |
| **修法** | 用 **`make diag`** 重建两张定标图（= `make calibrate` + `make compare`） |
| **顺带** | `compare.mjs` / `calibrate.mjs` 现在会打印**绝对路径**，不用再猜 |

### C7. Windows + Node 的两个小坑

* `node -e '…'` 想用 ESM 要加 `--input-type=module`（否则顶层 `await` 报错）
* 判断「模块是否被直接执行」**不能**用 `import.meta.url === \`file://${argv[1]}\`` —— Windows 下 `import.meta.url` 是 **三个**斜杠 (`file:///D:/…`)。要用 `pathToFileURL(path.resolve(argv[1])).href`。本工程封装在 `tools/util.mjs` 的 `isMain()`

### C8. GNU Make 在 Windows 下执行裸 `echo.` 会失败

| | |
|---|---|
| **现象** | `make help` → `process_begin: CreateProcess(NULL, echo., …) failed` |
| **原因** | 命令行里没有 shell 元字符时，GNU Make **不走 shell 直接 exec**，于是去找名为 `echo.` 的程序 |
| **修法** | Makefile 里不要用裸 `echo.`；把帮助文本交给 Node（本工程 `make help` → `node tools/build.mjs --help`） |

### D3. 定标的标准手段：**同锚点三方叠加比对**

```powershell
make diag        # = calibrate + compare
```

`out/calibrate/compare.png` 每行**四栏**：
**参照(China-Set-Tracks) · xUSSR(8bpp 4× 放大) · 我方 · 叠加(参照青 / 我方红)**

`out/calibrate/compare_zoom_<模型>.png` 是**裁到轨道附近 + 3×** 的版本，三张竖排
（上=参照 / 中=xUSSR / 下=我方）—— 整张图在屏幕上会被缩放，看不出纹理，**看质感必须看这张**。

为什么要有 xUSSR 那一栏：它是**成熟实现且与默认列车对齐**，
所以它的 bbox 就是我们竖向尺寸的"标准答案"。

> 实测（P1，相对瓦片原点，4x 像素）：
> `TRACK_X` — 参照 `y[18,108]` · xUSSR `y[20,112]` · 我方 `y[20,106]` ✅ 三方吻合
> `TRACK_UPPER` — 参照 `y[14,46]` · xUSSR `y[12,48]` · 我方 `y[9,58]`（我方略高，待收）

**判断"对不对"最快的方法就是这个**，比读数字快得多。

### D4. 报"某块不对"时：先认准**是哪一块**、再看它**在哪一层**，别猜着改 ⚠️

| | |
|---|---|
| **现象** | 人工说"某块不对"，我按自己的理解连改几轮、方向来回摆（先搬进 overlay → 撤回 → 换个搬法再搬），每轮都被否，白烧好几轮 |
| **原因** | 人工报的是**屏幕上的现象**，而我手里没有"能把现象指认到具体哪一块"的材料 ⇒ 只能猜是哪一块、猜它在哪一层。猜错时，改得越多离得越远 |
| **修法** | ① 先做**分层对照图**：从同一张表里取 underlay 与 overlay 两张精灵，**并排 + 放大**，第三格放叠加；<br>② 请人工在图上**圈出**他说的是哪一格里、哪个部件；<br>③ 圈的那块在**哪张图里**，就说明它现在**在哪一层** —— 这时"要不要换层、切在哪"才有依据；<br>④ 分界尽量对齐**已有的层边界**（某个常量、或相邻部件的边），别写死数值 |
| **已挡** | ❌ 流程类，靠自觉。判据很简单：**能不能用一张图把问题指认清楚** —— 做不到就先别动几何 |

> 与 A7 配套：A7 讲"为什么画了却看不见"，D4 讲"先问清是哪一块、再动手"。
