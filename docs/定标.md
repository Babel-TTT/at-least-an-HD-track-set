# 定标记录（P1）—— flatiso ↔ OpenTTD 轨道精灵口径

> 这是本项目**最底层的一份口径**。所有 `.model` 的坐标、所有 sprite 模板的槽位顺序、
> 所有摆放锚点都由本文件确定。
>
> 全部结论都有**实测证据**（`make render` + `node tools/calibrate.mjs` 产出的
> `out/calibrate/anchors.png`），不是推导出来的猜测。

## 1. 世界坐标 ↔ OpenTTD 瓦片方位

flatiso 的世界坐标（单位：瓦片）：

```
screen_x = (y − x) · 128          +x = 屏幕左下
screen_y = (x + y) · 64 − z·156.7673   +y = 屏幕右下
(0,0,0) = 占地西北角格角点
```

与 OpenTTD 的 `RemapCoords(x,y,z) = ((y−x)·2, (x+y)·4 − z·8)` 同构，
且 `_tileoffs_by_diagdir[NE] = {−1, 0}`、`slope_type.h`「the top corner of a tile is the
north-part of the tile」共同确定：

| flatiso 世界点 | 屏幕位置 | OpenTTD 名字 |
|---|---|---|
| `(0,0)` | 菱形**上**顶点 | `CORNER_N` |
| `(1,0)` | 菱形**左**顶点 | `CORNER_W` |
| `(0,1)` | 菱形**右**顶点 | `CORNER_E` |
| `(1,1)` | 菱形**下**顶点 | `CORNER_S` |

| 边中点（= 轨道接入点） | 屏幕位置 | DiagDirection |
|---|---|---|
| `(0, 0.5)` | 右上 | `NE` |
| `(0.5, 1)` | 右下 | `SE` |
| `(1, 0.5)` | 左下 | `SW` |
| `(0.5, 0)` | 左上 | `NW` |

**实测验证**：`probe_tile.model` 在四个格角放了 4 个不同颜色的柱子。
`out/calibrate/anchors.png` 第 2 行 view 0 显示
**红在上、蓝在左、白在右、黑在下**，与上表完全一致。

## 2. 六种轨道片的世界坐标线段

推导链（三处互相独立的源码证据一致）：

1. `_corner_to_trackbits`（`table/track_data.h:96-98`）：`CORNER_N → TRACK_BIT_UPPER`、
   `CORNER_W → TRACK_BIT_LEFT`、`CORNER_E → TRACK_BIT_RIGHT`、`CORNER_S → TRACK_BIT_LOWER`。
2. `_track_exitdir_to_trackdir`（同文件 61-68）：给出每个 track 从哪两个 DiagDirection 出入。
3. `slope_type.h:41` 明确「瓦片的上顶点就是北角」。

| OpenTTD track | 出入边 | **flatiso 世界坐标线段** | 屏幕形态 |
|---|---|---|---|
| `TRACK_X` | NE / SW | `(0,0.5)` ↔ `(1,0.5)` | `/` |
| `TRACK_Y` | SE / NW | `(0.5,0)` ↔ `(0.5,1)` | `\` |
| `TRACK_UPPER` | NE / NW | `(0,0.5)` ↔ `(0.5,0)` | 上角三角里的水平轨 |
| `TRACK_LOWER` | SE / SW | `(1,0.5)` ↔ `(0.5,1)` | 下角三角里的水平轨 |
| `TRACK_LEFT` | NW / SW | `(0.5,0)` ↔ `(1,0.5)` | 左角三角里的竖直轨 |
| `TRACK_RIGHT` | NE / SE | `(0,0.5)` ↔ `(0.5,1)` | 右角三角里的竖直轨 |

**旁证**：`China-Set-Tracks\vox\normal\60_32bpp.png`（trackbits 60 = 四条半格轨全有）
渲染出来是一个**方环**（中间有洞）—— 因为四条半格轨的道砟各是一条**贴着轨道方向的板带**，
四条板带沿瓦片四周排布，中间正好空出。这与下面的道砟几何规则完全吻合。

## 2.5 道砟几何：**统一的板带规则**（实测反推，2026-09 修正）

> ⚠ **曾经踩过的错**：半格轨的道砟被我做成「瓦片角上的三角形」（顶点在菱形上顶点、
> 底边是两条瓦片边）。这是**错的**，做出来又高又窄、像顶着一个尖帽子。
> 正确做法是**板带**，与直线轨道同一条规则。

### 规则

> **道砟 = 沿轨道方向、垂直于轨道约 0.36 格宽的一条板带，裁到瓦片内。**

| 轨道 | 轨道线 | 道砟带（世界坐标） |
|---|---|---|
| `TRACK_X` | `y = 0.5` | `0.32 ≤ y ≤ 0.68` |
| `TRACK_Y` | `x = 0.5` | `0.32 ≤ x ≤ 0.68` |
| `TRACK_UPPER` | `x + y = 0.5` | `0.33 ≤ x + y ≤ 0.67` |
| `TRACK_LOWER` | `x + y = 1.5` | `1.33 ≤ x + y ≤ 1.67` |
| `TRACK_LEFT` | `y − x = −0.5` | `−0.67 ≤ y − x ≤ −0.33` |
| `TRACK_RIGHT` | `y − x = +0.5` | `0.33 ≤ y − x ≤ 0.67` |

> ⚠ **半格轨的带宽是 `0.34`（不是直线的 `0.36`）**，这是刻意的：
> 同一条世界带宽，斜向与横/竖向在 2:1 投影里**投影宽度不同**（垂直方向 128 px/格、斜向只有约 114 px/格）。
> `0.34` 对应屏幕 43.5 px，与直线轨的 41 px 基本一致；而且枕木（2.5 m）能占满带宽的约 75%，
> 与参照包一致（原来 `0.48` 时枕木只占 51%，人工反馈「斜向的模型过于宽了」）。

半格轨那几行的带宽是 `0.48`（在 `x±y` 坐标里），换算成**垂直于轨道的宽度**是
`0.48 / √2 = 0.34` 格 —— 与直线的 `0.36` 基本一致。

### 实测佐证

| 对象 | 实测内容 bbox（相对瓦片原点，单位 px，4x） | 板带模型预测 |
|---|---|---|
| 参照 `01_32bpp.png#0`（直线） | `x[−84, 93]  y[18, 108]` | `y∈[0.32,0.68]` → `x[−87,87] y[20.5,107.5]` ✓ |
| 参照 `04_32bpp.png#0`（上半格） | `x[−87, 93]  y[14, 46]` | `x+y∈[0.26,0.74]` → `x[−92,92] y[16.6,47.4]` ✓ |

复现：`node tools/compare.mjs` → `out/calibrate/compare.png`（两边画在同一个锚点上叠着看）。

### 道砟板带宽度实测（2026-09，第三轮）

量法：在**轨道正中间**取 `|u| ≤ 8 px` 的窄窗，量垂直方向（`V`）的 alpha 跨度。
`TRACK_X`：屏幕方向 `(−2,1)/√5`、垂直 `(1,2)/√5`，屏幕上「1 格世界 y」在 `V` 上投影 `256/√5 = 114.5 px`。
半格：屏幕方向 `(1,0)`、垂直 `(0,1)`，1 格 = `128 px`。

| 对象 | 带宽 px | 格 | 米（1 格 = 13.9 m） |
|---|---:|---:|---:|
| 参照 `01_32bpp#0`（直线） | 51.9 | 0.453 | 6.30 |
| xUSSR `rail1` RTO_X（×4） | 62.6 | 0.547 | 7.60 |
| **我方** 直线 `probe_track_x#0`（`y∈[0.32,0.68]`） | 45.2 | 0.395 | 5.48 |
| 参照 `04_32bpp#0`（半格） | 32.0 | 0.250 | 3.48 |
| **我方** 半格 `probe_half_upper#0`（`x+y∈[0.35,0.65]`） | 20.0 | 0.156 | 2.17 |

**带宽比（半格 / 直线）**：参照 `0.55`，我方 `0.40` —— 半格偏窄。
收窄史：`0.48 → 0.34 → 0.30`（`x+y` 带宽），0.30 是照「参照的带宽比 × 我方直线」反推的。
⚠ 半格再窄下去枕木（0.180 长）就会顶出板带外。

### 断面（横剖面）—— **贴地，不抬高**（人工裁定 2026-09）

```
   rail  z = 0.026 ───────────────  轨顶（面 metal / 侧面 rust）
   sleeper z = 0.013 ─────────────  轨枕顶
   ballast z = 0.002 ─────────────  道床（贴地饰面）
   ground  z = 0     ────────────── 瓦片地面
```

| 层 | z 范围 | 说明 |
|---|---|---|
| 道床 | `0.0005` | **贴地饰面**，不是凸起的台子（原为 0.002，已压低） |
| 轨枕 | `0.002 → 0.013` | 扁平实体盒，间距 `0.05` 格 ≈ 0.70 m（加密） |
| 钢轨 | `0.013 → 0.026` | 轨距 0.1032 格；**顶面 `metal` / 侧面 `rust`（黄锈）** |

**总高 0.026 格 ≈ 4.1 px @4x**（参照图实测也只有 2~3 px 的微凸）。

> ⚠ **为什么不抬高**：瓦片内抬高的几何在跨瓦片绘制时会被邻格精灵遮挡 ⇒ 图形错位。
> 而且 OpenTTD 的竖轴是压缩的（`TILE_SIZE=16` / `TILE_HEIGHT=8`），同一个 z，
> flatiso 画出来是它的 **2.45 倍**。详见 `踩坑.md` A4 / A5。

**贴地怎么做出「不规则表面」**：不加高度，改用**贴地的小多边形**当碎石/散粒
（抬 `0.002` 防 z-fighting），靠材质冷暖差 + `grain` 出颗粒感。见 §2.6。

> ⚠ 这只是**几何**口径。真正的美术（碎石颗粒、轨枕样式、材质配色）属于 P2，
> 每个几何组开写前要过 D11 确认门。

### 2.6 ⚠ 「加面数」在 flatiso 里要先分清是什么面

**flatiso 是平面着色（flat shading），没有贴图。** 这有一个反直觉的后果：

> **共面的面，加多少个都等于一块大平板。**
> 把道砟顶面切成 200 个小四边形，只要它们还在同一平面、法线相同，
> 渲染出来和 1 个四边形**逐像素完全一样**。

所以「提高面数模拟不规则表面」的正确说法是 **「提高『法线朝向不同』的面数」** ——
要做的是**起伏的、倾斜的小面**（高度场 / 碎石棱面），不是把平面切碎。

flatiso 里做「碎石感」的正确顺序：

| 手段 | 机制 | 现状 |
|---|---|---|
| ① 断面形状 | 梯形肩坡 vs 平顶直壁 | ✅ 已做 |
| ② 材质颗粒 `grain` | 输出像素上的亮度抖动（**不是几何**） | ✅ 已在跑。`gravel` 的幅度 `0.060`，是除草地/植被外最高的一档（见 `core/materials.mjs` 的 `GRAIN_RULES`） |
| ③ 倾斜小面高度场 | 手工给顶点写不同的 z，让每个面的法线不同 | ⏳ 未做，这是下一步「不规则表面」的正解 |
| ④ 坡脚散粒 | 小 `box`/`prism` 撒在道床外侧 | ⏳ 未做 |

**量级提醒**：4x 下 `1 px = 0.008 格`。起伏做到 `0.004 ~ 0.012 格` 才有观感；
再细就是噪点，而且面数白涨。

**代价估算**：直线道砟顶面若做 `14×2` 高度场 ⇒ 约 `+28` 面（顶面）+ `+26` 面（两侧肩坡跟着起伏）。
`probe_track_x` 目前 113 面，做完约 170 面。9 个模型一组的总面数仍在几千量级，可接受。

## 3. ⚠ 锚点陷阱：不要直接用 flatiso 的 `xrel/yrel`

`gfx/openttd.json` 里的 `xrel/yrel` 是相对「**该朝向旋转后占地矩形的西北角**」的偏移。
而 OpenTTD 摆放精灵用的是相对「**瓦片原点**」，即瓦片菱形的**上顶点** —— 它**不随精灵内容旋转**。

对 1×1 模型，两者只在 view 0 巧合相等：

| view | flatiso 的 xrel/yrel | 正确值（瓦片原点） |
|---:|---|---|
| 0 | `−131, −19` | `−131, −19` ✓ 巧合相等 |
| 1 | `−3, −83` | `−131, −19` |
| 2 | `−131, −147` | `−131, −19` |
| 3 | `−259, −83` | `−131, −19` |

**照抄 flatiso 的 per-view 值会让第 2/3/4 个朝向整体错位半格。**

### 正确做法：用恒定的 `centerAnchor` 反推

`centerAnchor` 是「**占地中心投影**在精灵内的像素位置」，绕占地中心旋转因此**不随朝向变化**
（实测 4 个朝向都是 `[131, 83]`）。

```
占地中心 (cx, cy) = (占地宽/2, 占地深/2)
它相对瓦片原点的投影偏移 = ( (cy−cx)·HW , (cx+cy)·HH )      HW=128, HH=64
瓦片原点像素 = centerAnchor − 该偏移
NML 的 xrel = −原点像素x          NML 的 yrel = −原点像素y
```

已实现为 `tools/util.mjs` 的 `anchorToXrelYrel()`，`tools/sprites.mjs`（对账）与 `calibrate.mjs`
都走它。

**实测验证**：`out/calibrate/anchors.png` 里画了洋红色的瓦片菱形轮廓，
修正后**四个朝向都精确压住模型的瓦片地坪边缘**。

## 4. 朝向映射：flatiso 的步进是 OpenTTD 旋转的**逆**

记 OpenTTD 的四重旋转 `R`：`X→Y`、`UPPER→RIGHT→LOWER→LEFT`。

实测（`out/calibrate/anchors.png` 第 1、3 行）：

| 探针 | view 0 | view 1 | view 2 | view 3 |
|---|---|---|---|---|
| `probe_track_x` | `X` | `Y` | `X` | `Y` |
| `probe_half_upper` | `UPPER` | `LEFT` | `LOWER` | `RIGHT` |

⇒ **`flatiso view k ≡ R^(−k)`**

|---|---|---|
| `RTO_X` (`TRACK_X`) | `track_x` 族 | **0** |
| `RTO_Y` (`TRACK_Y`) | `track_x` 族 | **3** |

## 4.5 摆放事实来源：**手写**的 `src/rails/templates.pnml`（人工裁定 O2）

> 2026-09 改的。**这份文件没有生成器** —— 以前 `tools/gen-template.mjs` 会从
> `gfx/openttd.json` 重写它，导致手改会被静默覆盖；现在归人管，所有工具**只读**它。

### 名字怎么起

**模型名 = `models/` 下那个 `.model` 文件的文件名（去掉 `.model` 后缀）。**
一个文件 = 一个模型；渲染出几个朝向就有几个 view 号（0,1,2,3…）。
于是模板名固定为：

```
t_<模型名>_v<朝向号>          例：t_probe_half_upper_v0
```

一行数据是 7 个字段：

```
[x, y, w, h, xrel, yrel, "gfx/1x1.png"]
```

- `x y w h` —— 精灵在图集 `gfx/1x1.png` 里的矩形（4x 档，1×1 模型的格子固定 263×151）
- `xrel yrel` —— 相对【瓦片原点】的摆放偏移。**手调就改这两个数**：
  `xrel` 正 = 向右，`yrel` 正 = 向下
- **不要**写 flatiso 自己的 `xrel/yrel`（见 §3 的半格陷阱）

### 查名 / 对账工具

```powershell
make sprites                  # = node tools/sprites.mjs --sheet
```

它会：

1. 打印一张表：`模型#朝向` ↔ **引擎槽位**（`TRACK_X` / `TRACK_UPPER` …）↔
   模板名 ↔ **在 templates.pnml 里的行号** ↔ 当前 `xrel,yrel` ↔ `rect`；
2. 顺带**对账**：把文件里的值和按 `centerAnchor` 算出来的值比一遍，
   不一致就列出行号（这只是提示，**不会覆盖你的手改**。有意手调时可以无视）；
3. `--sheet` 出 `out/calibrate/index.png` —— 每个「模型#朝向」一格，全部画在
   **同一个瓦片锚点**上（洋红 = 瓦片轮廓，黄线 = 地面中心线），并打印行列号对照。
   图里没有字体，所以朝向号用**左上角青色竖条的长度**编码（view+1 段）。

模型改了尺寸或增删模型之后（图集会重新打包，**所有 `x/y` 都会变**），
用这个拿到正确值再手抄回去：

```powershell
node tools/sprites.mjs --emit     # 打印可整段粘贴的 template 块
```

### 标【手调】：让对账别再喊狼来了

对账用「按 `centerAnchor` 算出来的值」当基准，所以你**有意**的微调每次都会被报成
"不一致"。在这种行的注释末尾写 **`【手调】`**，它就会被单列成
`✎ 已标【手调】`，不再混在漂移里：

```
template t_probe_half_upper_v0() {
  [0, 0, 263, 151, -129, -21, "gfx/1x1.png"]      // az 0  TRACK_UPPER  【手调】
}
```

没标的行如果对不上，才是真信号（多半是模型改了尺寸导致图集重排 + 锚点移动）。

### 什么时候必须动

| 改动 | 要跟着改什么 |
|---|---|
| 改了 `models/*.model` 的 **footprint**（1×1 → 2×1） | 格子尺寸变 ⇒ 所有 `w h` |
| 增删模型 / 改渲染顺序 | 图集重排 ⇒ **所有 `x y`** |
| 只想让某个朝向偏几像素 | 直接改那一行 `xrel yrel` |
| 只是改了模型内部几何（宽窄高低） | 什么都不用改 |

> ⚠ `make check` 会做同一套对账（**只警告，不覆盖**），所以忘记同步时不会
> 静默出错。另外 `tools/clean.mjs` 以前会把 `templates.pnml` 当生成物删掉 ——
> 改成手写后已修好，`make clean` 现在不碰 `src/` 下任何文件。

## 6. 工程约束（实测）

1. **`models/` 必须是平铺的** —— flatiso 的 `listModelFiles()` 不递归
   （`core/bake.mjs`）。所以几何组不能建子目录，用文件名前缀区分（如 `G1_*`、`probe_*`）。
2. **`nmlc` 不自带预处理器** —— `#include` / `#define` 必须先过一遍 C 预处理器。
   本工程用 `gcc -E -x c -I.`（与 xUSSR、China-Set-Tracks 的做法一致）。
   行标记 `# 0 "file"` 是合法的（`#` 后跟空格），但 `#include` 不行。
3. **gcc 的 `#include "x"` 先相对「包含它的那个文件」找** —— 同目录的
   `railsprite.pnml` 引用 `templates.pnml` 要写相对路径，或加 `-I.`。
4. **`prism` 的多边形顶点顺序**：按「先 +x 再 +y」遍历（`cross_z > 0`），
   侧面法线才朝外。顶/底面法线由 `addPrism` 显式给定，不受影响。
