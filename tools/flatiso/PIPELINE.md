# flatiso 管线设计说明

**不用 Blender，不做实时 PBR / 真实光照。** 几何体手写成 `.model` 构件清单，
在一台"虚拟的老式离线渲染器"里以固定 2:1 等距正交视角批量烘焙成透明背景精灵，
产出直接进 OpenTTD GRF 的 32bpp 资源。

整条管线**只依赖 Node.js 标准库**：PNG 编解码器是自己写的（只用 `node:zlib`），
不需要 GPU、不需要 numpy/Pillow/任何 npm 包。

---

## 1. 设计立场

画风是「**平涂为主 + 柔和环境光 + 轻微 AO**」。这决定了三件事：

| 决定 | 实现 | 为什么 |
|---|---|---|
| **平面着色** | 每个多边形只算**一次**颜色，逐像素只再乘一个 AO 系数 | 面与面之间是干净的色块，边缘锐利。没有法线插值、没有逐像素光照、没有 BRDF |
| **明度分档靠光照，不靠描边** | 顶面 / 受光墙 / 背光墙 ≈ **241 / 188 / 153**（灰度值） | 等距视角下靠三个明度档读体积，这是"平涂"能读清楚的关键 |
| **半球环境光为主、平行光为辅** | 天顶偏冷、地面偏暖；平行光用 `sunSoftness` 抹开硬终止线 | "柔和环境光"，避免 Lambert 的死硬明暗交界 |
| **AO 只做轻微** | 只按 `aoStrength`（默认 0.34）压暗，而且对直射光的压制更弱 | 让建筑"坐"在地上、让檐下和院子里有暗部，但**不把平墙压脏** |
| **有纹理，但不是贴图** | 瓦垄 / 砖缝 / 板肋 / 腰线全部是**真的有宽度的几何线脚**（见 §6） | 手感来自"一件件做出来的线脚"，而不是图案噪声。线脚跟着透视收窄、吃 AO、进描边通道 |

## 2. 投影：为什么 zPx 是 156.767

```
screen_x = (y - x) · HW          HW = tilePx/2 = 128
screen_y = (x + y) · HH - z · zPx    HH = tilePx/4 = 64
```

`tilePx = 256` 时 1×1 瓦片投成 **256 × 128** 的菱形 —— 严格 2:1，
瓦片一条边水平跨 **128 px**、竖直跨 64 px。

**`zPx` 不是随手挑的。** 要求"2:1 的菱形 + 真正的正交相机"，竖直缩放就被唯一确定了。
设相机方位角 45°、仰角 φ（从水平面算）、整体缩放 S：

```
screen_x = S/√2 · (x - y)                    →  S = HW·√2
screen_y = S·(cosφ/√2·(x+y) - sinφ·z)
```

2:1 要求 `x+y` 的系数等于 `HH`：`HW·cosφ = HW/2` → `cosφ = 1/2`，**仰角恰为 30°**。于是

```
zPx = S·sinφ = HW·√2·(√3/2) = HW·√6/2 ≈ 156.767
```

只有这个值，一个 1×1×1 的立方体三条棱才等长，烟囱、楼层的高度比例才不失真。
传更小的 `zPx`（例如 128）会得到"压扁"的观感 —— 那是刻意的风格选择，不是几何正确。

**手性对齐 OpenTTD。** `+x` 朝屏幕左下、`+y` 朝屏幕右下 —— 与
`RemapCoords(x,y,z) = (2*(y-x), x+y-z)` 完全一致。所以按 RemapCoords 摆出来的
位置不需要额外镜像。想换成相反手性用 `makeView({ mirror: true })`。

## 3. 与 OpenTTD 的关系

| 项 | OpenTTD 原版 | 本管线 |
|---|---|---|
| 一瓦片 | 64 × 32 px | **256 × 128 px**（= 4 倍，正好是 4× 额外缩放档） |
| 世界单位 | 16 / 瓦片 | **1 / 瓦片** |
| 色深 | 8bpp DOS 调色板 | **32bpp RGBA**（不做量化）；8bpp 底图可后续量化补 |
| 精灵锚点 | `xrel/yrel` 相对格子锚点，单位是精灵像素 | 同；见 §4 |

`out/atlas/openttd.json` 给逐条 sprite 的 `rect / xrel / yrel / zoomLevel / footprintRotated`，
以及摆放公式。**NML / GRF 的编写不在本工程范围内** —— 这里只负责出图和把"怎么摆"讲清楚。

**关于 8bpp 底图**：OpenTTD 的常规结构是「8bpp 底图 + 32bpp alternative（4× 档）」。
本管线只出 32bpp。要补 8bpp 底图，把 RGBA 输出按 DOS 调色板最近色量化
（索引 0 作透明、避开 215–226 未用粉与 227+ 动画色）即可 —— 这一步没有做进管线，
因为当前目标就是 32bpp。

## 4. 取景与锚点

这一节是"**排列规则、便于程序使用**"的全部内容。

### 4.1 绕占地中心旋转

朝向不是靠转相机实现的，而是**把模型绕占地中心旋转** r×step 度后固定相机渲染。
等价于反向转相机，但有两个好处：

* 占地菱形的**中心**始终落在同一个屏幕点 —— 锚点不随朝向变化；
* 用 90° 的整数倍时，1×1 / 2×2 的占地仍然映射到自己，不会跑偏。

（注意：**必须绕占地中心**。绕世界原点转会让建筑在屏幕上下漂。）

### 4.2 同占地统一格位

1. 对每个朝向求"内容包围盒 ∪ 占地菱形四角 ∪ 显式 `zmax` 天花板"；
2. 取**所有朝向的并集**当取景框 —— 于是同一栋楼的 4 个朝向格位完全一致；
3. 再对**同一占地的所有模型**取最大值当作图集格位；
4. 格位里"占地中心投影"的像素位置在整张图集里是**常量**。

结果：

```
1x1 → 格位 263×202, anchor (131,134)
2x1 → 格位 391×291, anchor (195,191)
2x2 → 格位 519×563, anchor (259,431)
```

引擎只记 `cell` 与 `anchor` 两个值，加上 `(col,row)` 就能抠出任意一张。

### 4.3 每张精灵就是整格

`rect` 一律是整格矩形（不是内容的紧包围盒）。代价是一点透明像素，
换来的是**图集是严格规则网格**：`rect = (col·cellW, row·cellH, cellW, cellH)`。
内容在格内的偏移记在 `content` 字段，只用于调试。

### 4.4 双锚点

| 字段 | 含义 | 什么时候用 |
|---|---|---|
| `anchor` | 格位里"**占地中心**在地面的投影"的像素 | 自研引擎；绕中心对齐最稳 |
| `xrel/yrel` | 取负后是格位里"该朝向的**占地西北角格角点**"的像素 | OpenTTD / NML spriteset |

`xrel/yrel` **逐朝向不同**是对的：模型绕占地中心转 90° 之后，那片地皮的西北角
在模型自己的坐标系里换了个地方。例：`res_cottage` 四个朝向分别是
`(-131,-70) / (-3,-134) / (-131,-198) / (-259,-134)` —— 正好是一个绕圈的正方形。

**2×1 的 90°/270° 朝向占地会变成 1×2**，矩形记在 `footprintRotated` 里
（例如 `[[0.5,-0.5],[1.5,1.5]]`）。GRF 侧要么接受占地跟着转，要么只取 0°/180° 两个朝向。

## 5. `.model` 手写清单

**模型是资产，不是程序。** 一个 `.model` 只有一行行字面量构件：
没有循环、没有条件、没有随机数。跟在建模软件里一件件摆出来是一回事。

```
name res_cottage
group residential
footprint 1 1
zmax 0.70

plate 0.020 0.020 0.980 0.980 0.006    grass
box   0.100 0.080 0.000  0.900 0.620 0.035   stone_dark
gable 0.115 0.095 0.885 0.605 0.320 0.480  x  0.045  roof_tile  side=plaster_cream
win   +y 0.605  0.170 0.330 0.100 0.250   glass  frame=trim_white  mull=2
door  +y 0.605  0.440 0.560 0.035 0.235   wood_dark  frame=trim_white  step=2
tree  0.800 0.780 0.115 0.320        trunk  foliage
```

一行一个构件：`关键字 位置参数... [键=值...]`，裸词当布尔标记，`#` 起注释。
构件统一按「**朝向 → 平面坐标 at → 面上矩形 → 材质**」排列。

* **基础图元**：`plate` `box` `quad` `poly` `prism` `cyl` `gable` `hip` `shed`
* **构件**：`win` `door` `rail` `step` `awning` `sign` `chimney` `roofunit` `tank` `tree` `hedge` `lamp`
* **通用修饰**：`gid=N` 复用面组、`noocc` 不参与 AO 遮挡

`win` 之类的构件是**标准配件**（跟建模软件里的门窗组件一样），
每扇窗的高度、位置、是否亮灯仍然是逐条写死的 —— 它不是生成器。

**面组（gid）决定哪里有线。** 每条构件默认独占一个面组，构件之间自然出现分缝线；
同组内折角超过 `creaseAngle`（默认 32°）也会画线。所以"哪里有线"是建模时决定的，
渲染器不擅自加线。

## 6. 线脚：纹理是怎么来的

参考项目（`建筑测试/tools` 的 `generate.py`）那种"纹理感"来自两个手段：
**逐像素随机抖动**（地面撒 50 个随机点、草地按 2:7:1 随机铺三个相邻绿）
和**手画的 1px 线脚**（5 道瓦垄 × 每垄 6 片错缝、砖缝、零宽度的窗竖梃）。

本管线只取后者，并且把它变成了**建模语言的一部分**：

| 手段 | 实现 | 为什么不用另一种 |
|---|---|---|
| **几何线脚**（采用） | `addStrip` 画一条有宽度的四边形，`addCourses` 铺成排分缝 + 错缝 | 跟着透视走、会吃 AO、会进描边通道；线宽可控，不会因为分辨率变化而糊掉 |
| 逐像素图案函数（不用） | —— | 会把"平涂"变成"噪声"；面不再是纯色，和 §1 的立场冲突 |
| 噪点抖动（不用） | —— | 同上，而且它本质是"用噪声凑出层次"，不是真的把结构做出来 |

### 6.1 两条语法

```
# 一条线脚：给定两端点和所在表面的法线，宽度向面内铺开
strip  x0 y0 z0  x1 y1 z1   <法线>   <线宽>   <材质>   [lift=] [gid=]

# 一片平面上的成排分缝
courses <朝向> at  u0 u1 v0 v1   <rows> <cols>   <材质>   [w=] [stagger=] [lift=]
```

`courses` 的坐标约定：±x 面 `u=y, v=z`；±y 面 `u=x, v=z`；±z 面 `u=x, v=y`（`at` 就是 z）。
`rows` 是分垄数（产生 `rows-1` 条横缝），`cols` 是每垄的错缝片数。
所以：**砖墙** `rows=8 cols=8`、**幕墙竖梃** `rows=1 cols=9`、
**金属板肋** `rows=1 cols=18 tileStagger=0`、**腰线** 用 `strip`。

### 6.2 屋面图元自带瓦垄开关

屋面不是轴对齐平面，手算法线和坡向很容易错，所以 `gable` / `shed` 直接带开关：

```
gable ... roof_tile  tileRows=8  tileCols=7  tileW=0.011  tileMat=roof_tile_seam
shed  ... roof_metal tileRows=1  tileCols=18 tileW=0.008  tileMat=metal_rib  tileStagger=0
```

`addTiling()` 在坡面上以「脊线为原点、脊向为 U、坡向为 V」建平面坐标系，
再交给同一套 `addCourses`。等距投影下横垄会随坡面自然收窄，不需要额外处理。

`hip`（庑殿顶）南北两坡是梯形，横垄长度会变而 `addCourses` 只处理平行四边形，
所以**没有**给 hip 铺瓦垄 —— 这是刻意的，宁可不做也不做错。

### 6.3 缝的颜色

线是"凹缝"，所以用比基材暗一档的同色系；金属板肋是凸起受光，反而用亮一档。
`materials.mjs` 里有一组 `*_seam` / `metal_rib` 专供此用，全部是手调的字面量，
不走"自动变暗 20%"那种推导 —— 颜色是要看的，不是算的。

### 6.4 线宽怎么定

`tilePx=256` 时世界单位 → 屏幕：水平方向约 143 px/单位，竖直方向约 157 px/单位。
所以一条 **0.011** 宽的瓦缝在屏幕上大约 1.5 px —— 足够看清，又不会变成卡通描边。
本管线全部线脚落在 **0.008 ~ 0.014** 这个带里。

## 7. 观感预设与色彩分级

| 预设 | 观感 |
|---|---|
| `stylized`（默认） | **风格化预渲染资产**：光比大、阴影偏冷受光偏暖 |
| `soft` | 上一版的观感，留着做 A/B：光比软、颜色灰 |
| `bright` | 展厅感：环境光更多、暗部更浅 |
| `dramatic` | 强侧逆光 + 每通道分档，最"版画"的一档，适合封面图 |

（预设里的 `outlineSilhouette / outlineCrease / outlineTint` 只在传 `--outline` 时生效。）

### 7.1 `stylized` 做了什么

从 `soft` 到 `stylized` 一共动了四处，按实际贡献从大到小排：

1. **拉开光比**。环境光 0.46 → 0.24，平行光 0.66 → 0.88，柔化 0.38 → 0.22。
   三档明度从 `224 / 190 / 172`（灰度）变成 `241 / 188 / 153`。
   数字上看只差一点，但这三档之间**不再有中间调** —— 体积是一刀切出来的，
   而不是靠渐变糊出来的。

2. **描边「色持」(color hold)**。轮廓不再压成黑，而是往深蓝紫收敛
   （`outlineTint = [0.84, 0.90, 1.12]`），强度也从 0.64/0.82 提到 0.46/0.72。
   纯黑轮廓会让画面显脏、显廉价 —— 这是插画和预渲染资产里最常见的做法。

3. **冷暖分离调色**。阴影加暖负、蓝正，高光反之。让"暗部"读成冷、"亮部"读成暖。

4. **对比 + 饱和**。`contrast 1.18 / pivot 0.70`、`saturation 1.14`。

### 7.2 `pivot` 为什么必须可调（踩过的坑）

分级里的对比第一版写成 `c += k·(c-0.5)·(1-|2c-1|)`，看着像个 S 曲线，**实际把对比做小了**：

```
墙面 0.60 → 0.648     顶面 0.895 → 0.945      差距 0.295 → 0.297
```

因为我们的图整体偏亮（大片墙面落在 0.55~0.9），支点在 0.5 时两侧**都被往上推**。
支点必须落在图的实际中调上才会真正拉开：

```
pivot=0.70, k=1.18:   0.60 → 0.582     0.895 → 0.930      差距 0.295 → 0.348
```

所以 `contrast` 的语义是**系数 k（1 = 不变）**而不是"0 = 关闭"，
并且必须配一个 `pivot`。这个坑记在 §10。

### 7.3 旋钮在哪

* 光照 / AO / 描边：`core/look.mjs` 的预设对象
  （`sun / sunColor / skyColor / groundColor / ambient / sunIntensity /
  sunSoftness / aoStrength / aoDirect / outlineSilhouette / outlineCrease /
  creaseAngle / outlineTint`）
* 分级：预设里的 `grade` 子对象 → `makeGrade()`，
  `contrast / pivot / saturation / splitAmount / shadowTint / highlightTint /
  steps / stepPull`

改预设后 `node tools/inspect.mjs <名字> --preset <预设>` 可以立刻 A/B。

### 7.4 材质颗粒（grain）

线脚解决的是"**结构**"（哪儿有洞口、哪儿有分缝），颗粒解决的是"**材质感**"——
大块平涂的墙面在 256px/瓦片下会显得空，一层极低幅度的逐像素噪点能让它读成抹灰/砖/瓦。

**幅度按材质族给**，写在 `materials.mjs` 的 `GRAIN_RULES` 里，不逐个材质标：

| 材质族 | 幅度 | 材质族 | 幅度 |
|---|---|---|---|
| 抹灰 `plaster_*` | ±4.5% | 砖 `brick_*` | ±5.5% |
| 混凝土 `concrete*` | ±4.8% | 瓦 `roof_tile/shingle` | ±5.0~5.5% |
| 石 `stone_*` | ±3.2% | 沥青 / 铺装 | ±5.5% |
| 植被 `grass/foliage` | ±7.0~7.5% | 金属 `metal*` | ±2.2% |
| **线脚 `*_seam` / 玻璃 / 招牌 / 涂装** | **0** | | |

为 0 的那几类是刻意的：线脚本身就是 1~2px 的深色细线，加颗粒只会把它糊掉；
玻璃和招牌是光洁面，加颗粒显脏。

**采样必须落在输出像素上，不能落在子样本上。** 这是整个实现里最关键的一点：

* 光栅内层循环里本来就有逐像素的世界坐标，直接在那里乘是最省事的写法 ——
  但那是**子样本**分辨率。ss=3 时每输出像素有 9 个子样本，颗粒会被平均掉一部分，
  结果是**强度随 `ss` 变化**（换 `--ss 2` 图就变了，破坏"可复现"这条底线），
  斜面上还会起摩尔纹。
* 所以挪到解析阶段：用**像素中心的屏幕位置 + 该面的平面方程**反解出世界坐标。
  屏幕投影是线性的，两个方程加平面方程正好三个未知数：

  ```
  (y - x)·HW = sx ;   (x + y)·HH - z·zPx = sy ;   n·p = d
  ```

  Cramer 直接解，每个有内容的像素约 30 次乘法。很便宜，而且换来的是**严格锁定在
  输出像素网格上**。

实测验证（`res_cottage`，同一朝向）：

```
关颗粒  ss2 vs ss4 差异 21.32%   ← 全部来自抗锯齿边缘
开颗粒  ss2 vs ss4 差异 21.46%   ← 只多 0.14 个百分点
```

如果颗粒是在子样本层算的，这个数字会接近"所有内部像素都不同"。

**颗粒锚定在世界空间**（不是屏幕空间），所以它跟着模型旋转 ——
同一面墙在四个朝向里是同一片颗粒，不会"游"。

**和分档的冲突**：`dramatic` 预设开了每通道分档（`steps=9`），
噪点一旦跨过分级边界就会在相邻两档之间反复横跳，出来是一片椒盐点。
所以那一档默认关颗粒。

**代价**：7 栋 × 4 朝向 @ `ss=3`，开颗粒 14.9 s / 关颗粒 12.2 s，**+22%**。
比预估低，因为颗粒只跑在"有内容的像素"上（约占格位 30~45%）。

**开关**：`--no-grain` / `--grain-amount=N` / `--grain-scale=X`（世界单位，1 输出像素 ≈ 0.0072）。

### 7.5 描边通道：**默认关闭**

管线里有一个"面 ID 描边"通道（折角 / 面组边界 / 剪影），**默认不跑**，要就显式传
`--outline`（对应 `renderSprite` 的 `opts.outline === true`）。

为什么关掉：它在**低面数、大块面**的模型上是对的 —— 给干净的面与面之间加一道细线。
但在**高面数、细碎**的模型上会失效。实测 `com_bldg90`（5552 三角面）：

```
不透明像素            : 184122
描边改动的像素        : 83840   (45.54%)
平均亮度 开描边        : 115.1
平均亮度 关描边        : 136.5    ← 整体压暗 16%
全量构建 开 → 关       : 21.2 s → 13.9 s
```

立面全是小盒子（28 樘带窗 × 18 根竖梃、36 台空调外机、栏杆、七道腰线……），
几乎每个像素都挨着某条边 —— 这时候描边不再是"勾轮廓"，而是**给整张图蒙了一层暗网**。

还有个更隐蔽的问题：描边的色持是 `outlineTint = [0.84, 0.90, 1.12]`（往蓝紫推）。
这个值是在**奶油色 + 红瓦**的小屋上调的，那时候它把轮廓从死黑救成深蓝紫、是对的。
但白色面砖被它一乘：

```
(228, 226, 218) × 0.72 × (0.84, 0.90, 1.12) = (138, 146, 176)   ← 灰蓝
```

**在白色建筑上，蓝紫色持直接读成"灰"。** 所以关掉之后，剩下的灰线应该全部来自几何
（铝合金窗框 `metal_alu`、檐沟落水管 `metal_pale`、压顶 `granite_grey`、
面砖分格缝 `tile_white_seam`、窗洞侧壁、转角 AO）—— 那些是建模时有意加的，不是通道画的。

想让描边只留外轮廓、不要盒子之间的折角线，把 `outlineCrease` 设成 1 即可。

## 9. 两套自检各查什么

`node tools/check.mjs` 只查**渲染管线**的不变量，不查好看不好看：

1. **投影** —— 1×1 菱形必须正好 256×128，一条边水平跨 128 px；`+x` 必须朝屏幕左下。
2. **几何** —— 占地不越界、不穿地、无退化面、占地是整瓦片。
3. **取景** —— 每张精灵四周至少 1px 全透明（等于没被裁掉）；占地菱形四角必须完整落在格位内。
4. **一致性** —— 同占地的模型共用同一个格位且都装得下。
5. **确定性** —— 同一配置连渲两次，逐像素 sha256 必须相同。
6. **GRF** —— 图集尺寸是 `格位 × 行列` 的整数倍；`rect` 与 `col/row` 对应且不重叠；
   锚点落在格位内。

`node tools/verify.mjs --rebuild` 只查**磁盘上的产物**：

1. **跨进程复现** —— 重跑一次 build，三张图集必须**逐字节相同**
   （`atlas.json` 里只有 `generated` 时间戳允许变，比对时剥掉）。
2. **PNG 格式** —— 必须是合法 PNG、**色型 6（真彩 + Alpha，即 32bpp）**，
   不能是索引色或被压成 RGB。
3. **透明背景** —— 内容占比必须在 3%~99% 之间（既证明背景真的是透明的，
   又证明图集不是空的）。
4. **不裁切** —— 每个格子的四条边框必须全透明。
5. **元数据自洽** —— `openttd.json` 逐条与 `atlas.json` 对得上；
   `spritesets.nml` 引用的图集文件都真实存在。

## 10. 实现要点与踩过的坑

这些都是实测踩过的、值得记下来的地方：

* **深度的 `depthK` 忘了导出，是最阴的一脚。** `project.mjs` 里算了 `depthK`
  但没放进返回对象 → `view.depthK === undefined` → `dz = NaN` →
  `NaN <= zb[di]` 恒为 **false** → 深度测试**永远通过** → 谁最后画谁覆盖。
  症状是"模型看起来渲染对了，但某些大平面糊住了所有东西"，极难反推。
* **屋顶绕反了不会报错，只会变黑。** 面还是画出来的，只是法线朝内 → 光照算成背光。
  所以 `mesh.mjs` 里屋顶/棱柱这类容易绕错的图元一律走 `addQuadO/addTriO`：
  显式说明"这一面应该朝哪"，由 helper 按 Newell 结果决定要不要反序。
* **必须做背面剔除，否则单面片会"凭空糊一块黑板"。** 招牌、栏杆、窗框是零厚度单面片；
  相机看到它背面时它仍然被光栅化，而它在深度上更靠前 —— 会把后面整栋楼糊掉。
  剔除后既修了这个 bug，又省掉约一半光栅化。
* **取景必须取"所有朝向的并集"**，否则同占地不同朝向的精灵尺寸不一致，
  规则网格就散了。还要把**占地菱形四角**和显式 `zmax` 一起算进去。
* **旋转必须绕占地中心**，不能绕世界原点，否则建筑会在屏幕上上下漂。
* **精灵尺寸要用整格，不要用内容紧包围盒。** 一开始用紧包围盒，
  结果同组里高矮不同的楼尺寸各异，"所有精灵一样大"的承诺就没了
  （`tools/check.mjs` 会直接报出来）。
* **AO 要按"空间位置"分组算，不能按顶点算。** 顶点是按面复制的，
  按顶点算会让相邻面的公共棱上出现明暗错缝。
* **台阶这类沿法线摊开的构件要算进占地**，否则会越界（仓库的装卸台阶就这么踩过一次）。
* **坡屋顶的法线很容易漏一个负号，而且不会报错。** `addShed` 一开始把坡面法线写成
  `norm([0, -rise, |run|])` —— y 分量符号反了。面照样画出来、照样被剔除通过，
  只是**一整天都偏暗**，看半天才反应过来。正确写法是 `norm([0, rise, run])`：
  沿坡向是 `(0, run, -rise)`，外法线在 YZ 平面内转 90° 取朝上的那个。
  凡是"看起来对但就是不对"的面，先打印法线。
* **线脚必须沿法线抬起来一点**（`lift = 0.0018`，约 0.28 px），
  否则和表面共面、深度相等，`dz <= zb` 会看运气。抬起来之后既不会闪，
  也不会在掠射角上看出"浮"。抬起量要远小于线宽（线宽 0.011），否则会变成"贴纸"。
* **对比曲线的支点不能写死在 0.5**。第一版写了个看着像 S 曲线的
  `c += k·(c-0.5)·(1-|2c-1|)`，结果对比**反而变小**：我们的图整体偏亮，
  支点在 0.5 时两侧都被往上推。必须把 pivot 做成参数（见 §7.2）。
* **改分级参数时别连着改两个变量**。中间有一版同时把 `contrast` 提到 1.30
  又把 `splitAmount` 提到 1.25，结果红瓦被蓝味的暗部调色冲成砖褐色 ——
  分离调色的量级要按"暗部占画面的比例"给，1.25 太大了，0.4 才是对的。
* **取景实测优于解析**：先量真实内容范围再整数平移进格位，不重采样、一次到位。

## 11. 性能

单台普通 CPU、纯 JS（Node 24）：

| 配置 | 7 栋 × 4 朝向 |
|---|---|
| `ss=2` | 约 9.5 s |
| `ss=3`（默认质量） | 约 11.5 s |

瓶颈是光栅化（逐子采样点循环）。要更快：`--ss 2`、`--rotations 2`、`--only <名字>`。
AO 烘焙是毫秒级的（按位置分组 + AABB 网格加速）。

**线脚的代价**：加上线脚后三角形数从每栋 90~400 涨到 110~505（工厂砖缝最多），
光栅化时间只涨了约 15% —— 因为线脚是细长条，覆盖的像素本来就很少。
这笔开销换来的是整片表面从"一块纯色"变成"有材料的表面"，很划算。
